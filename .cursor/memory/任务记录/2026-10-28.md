### 任务 7：真机回归暴露的规划路径断链（run 20261028-151850 W3 暂停）
- **现象**：整句「编译代码，打开编辑器，给level3的fps游戏增加道具手榴弹…」拆出 W1/W2/W3，W3 `implement_grenade` 槽位明明填了 `level: "level3"`，却暂停「槽位是空的，不猜」
- **根因（三层）**：
  1. `plan_windows.resolve_slots` 没有 `implement_grenade` 分支，掉进通用兜底 `resolve_name(slots["target"])` → 空槽位误报（implement_grenade 的执行/判词映射都接了，唯独规划解析漏了）
  2. `resolve_level("level3")` 会解析成不存在的 `/Game/Maps/level3`——用户嘴里的「level3」是 `L_NewTest3` 的昵称
  3. 就算前两层修好，L1 合同把「关卡内容」写成 editor_assert 条款只绑 launch 扇，复合扇的 automation 收口勾不动它，整句会被误判「部分完成」
- **修复**：
  1. `resolve_slots` 加 `implement_shooter`/`implement_grenade` 分支（解析关卡 + automation_filter）；`_default_title` 补 implement_grenade
  2. `plan_windows.resolve_existing_level`：要求关卡已存在的动作（open_level / implement_shooter / implement_grenade）在包不存在且原词是裸名昵称时，按尾号数字对磁盘现有关卡唯一匹配（level3 → L_NewTest3，带 alias_note）；多候选暂停问全名，零候选拿原解析去执行层诚实失败；`create_level` 不走别名
  3. harness 绑定：`_window_ids_for` 的 editor_assert 条款加认复合动作扇；`build_criteria` 给带 automation_filter 的复合扇补 automation 条款；`_implement_shooter`/`_implement_grenade` 成功时落一条 editor_assert 副判词（关卡内容核对），让 L1 的关卡内容条款有证据可勾
- **结果**：`check_implement_grenade` 加 3 条回归断言全绿；受影响的 16 项检查重跑全绿；同句重跑 W3 应物化为可执行扇（level=L_NewTest3 + AIAgent.Fps.Grenade）
- **经验**：
  - 「执行、判词、规划解析」三件套必须同时接——接了执行和判词、漏了 resolve_slots，暂停窗比缺口更迷惑（缺口至少说真话）
  - 昵称解析的诚实边界：唯一匹配才接受、多候选暂停、零候选不编；create_level 这类「允许新名字」的动作绝不能被别名劫持

3. **执行序是架构约束不是细节**：写码→编译→回连→放置的次序要由代码钉死，不能指望模型排出正确次序。
4. **并发资源要有锁**：UBT 单实例，跨进程编译锁是底线。
5. **模型非确定性要有形状守卫**：同一句话不同轮走出不同假路径（假绑定→假成功、编造 external_dep→假等待），每个假路径都需要一个廉价的代码侧守卫接住。

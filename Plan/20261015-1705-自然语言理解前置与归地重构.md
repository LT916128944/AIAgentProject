## 1. 结论

今天的五次失败（`20261014-195443` 到 `20261015-165155`）没有一次出在执行器、裁判或者动作目录上。全部出在**句子 → 动作目录**这一层，而这一层现在是正则：

| 当天现象 | 接不住的那一层 |
| --- | --- |
| 「将蓝图 /Game/BP_TestEnemy 放到场景」→ 必停「编译蓝图」扇 | 规则把「编译代码」误绑成「编译那张蓝图」 |
| 任务书确认后窗口被 LLM 重编，丢掉快路径解析好的创建/放置 | 生成器产出直接替换候选（已修：继承候选） |
| 环：W2→W2 | 候选 id 换算时机（已修：两遍换算） |
| 「再放一个到场景中」→ 放置路由不触发 | `_PLACE_RE` 四种措辞之外的盲区 |
| 「位置不要与已有的叠一起」→ 固定放 `(0,0,100)` | 动作参数没有「约束」槽（已修：错开 50 uu） |

结论：**继续往正则里加措辞是在给缓存手写条目**。措辞无限，正则有限。这一层该换成「大模型理解 + 学习沉淀」，但模型只负责**选目录内动作、填槽位名、声明约束**，路径、父类、refPath 一律由代码归地，裁判照旧不由模型宣布成功。执行器、动作目录、被验证过的归地逻辑（索引命中直连 / C++ 类推导新建 / 暂停问 `r`）全部保留。

三句话总结：**模型在前只做理解和选动作，代码在中做归地和裁判，跑赢后沉淀成快路径**。今天手写的那批路由不删，退役为 `learned_routes` 的种子和 L1 失联时的兜底。

## 3. 为什么不是「让模型直接规划一切」

用户直觉是「自然语言先过一遍大模型，拆成要调的脚本」。方向对，但要挡三个坑：

| 坑 | 挡法 |
| --- | --- |
| 模型拍脑袋编 `/Game` 路径、工具全名（幻觉） | 模型只许填动作 id 和槽位名（原始 token，如 `BP_TestEnemy`）；路径解析 100% 在 L2 代码做，沿用「不猜」 |
| 每句必付一次模型调用的延迟和 token | L0 缓存（learned_routes）先挡重复句式；理解器只在弱命中/未命中时调用；成本和调用与否记进 events |
| 评测变得不确定，离线回归失效 | 意图 JSON 结构固定，评测用 stub 理解器注入期望意图离线断言 L2 落地链；L3 模板本身也是纯数据可离线测 |

规划者（菜单 3 的 planner）和任务书生成器保留：**理解器接管的是「一句话 → 动作序列」这一段**，长句出任务书、范围 Hag 拆分仍走现在的路径，只是它们的候选窗口来源统一成 L2 归地产物。

## 4. 实施顺序（下一轮对话逐段做，每段有验收表）

### P1 意图层与理解器

- 新文件 `agent/intent.py`：
  - `INTENT_SCHEMA`：`{query, goals:[{action, slots:{角色:原始token}, args:{数量/位置约束…}}], constraints:{editor, pie, save:false}, unresolved:[...]}`；
  - `validate_intent(data, query) -> dict`：动作必须在 CATALOG；槽位必须是该声明的槽位名；未知字段丢弃并列进 `dropped`（抄 `validate_brief` 的代码验收风格）。
- 新文件 `agent/understand.py`：
  - `understand(query, complete=None) -> Intent | None`：系统提示 = 动作卡片 + 三条铁律（只选表内动作／只填槽位名不编路径／分类推不出的写进 unresolved）；用户消息 = 原句 + 3 条检索标题，控制在 1KB 上下；输出 JSON only。
- `plan_windows` 主链改造（`agent/plan_windows.py`）：
  - `_rules_cover` 语义收紧：拆出任何 `ok=False`/`needs` 的步骤就算「弱命中」，不再当「手写规则能拆开」；
  - 顺序变为：L0（learned + 规则强命中）→ L1 `understand` + `materialize` → 非 JSON（老规划者）只做任务书兜底；
  - L1 说不出合法意图（表外动作、解析失败）→ 回退现有行为（暂停或叫规划者），重试上限 1 次。

**验收（离线）**：把今天五次失败的原话写进 `eval/tasks/side/planning-corpus.json`，配 stub 理解器注入期望意图，断言拆出的窗口动作序列；再用真理解器跑一遍记录 intent 原文进 events。手写规则现在能拆的句子（移动 Cube、编译 BP_Gun）在 L0 命中，`understand_called=false`。

## 5. 明确不做

- 不给模型 830 个工具 schema，不发明工具全名；动作卡片只有 `id + 槽位 + 一句说明`
- 不把 `--query` 接成 Cursor 每句话的默认动作
- 槽位解析不上语义向量，仍是符号匹配 + 唯一性；零条或多条就 `r` 一次
- 保存 / PIE 默认值不动；`UE_ALLOW_BLUEPRINT` etc 开关不动
- 不换模型、不换供应商、不做多模型分工
- 手写规则先不删（兜底 + 种子），等 learned_routes 在旁路题集上连续稳定后再议
- 不做隔离上下文的子代理（沿用 10-14 那份的决定）

# Harness框架设计

## Harness安全护栏

### Harness 安全护栏：AI Agent 越权操作如何彻底杜绝？

不靠“教育” Agent 别做坏事，而是把危险权限、危险命令、危险路径，统一锁进 Harness 的系统护栏里。

- 最小权限
- 沙箱隔离
- 策略网关
- 审批拦截
- 全链路审计

**Agent 会思考**

但它只能提出“行动请求”，不能直接碰宿主机、根目录、密钥和生产资源。

**Harness 会裁决**

所有动作必须先经过能力映射、策略校验、风险分级、审批和沙箱执行。

**危险命令不可达**

不是“尽量不要执行”，而是根本没有那把刀、没有那扇门、没有那个权限。

**安全动作可验证**

允许的只有白名单能力；执行结果可回放、可追责、可熔断、可回滚。

Harness 的核心：想做 ≠ 能做

### 第 3 层：策略裁决与审批网关

**动作解析器**（解析）

把请求拆成“对象、动作、范围、环境、风险”五元组。

**策略引擎**（规则）

白名单优先、黑名单兜底、环境差异化策略统一在 Harness 中执行。

**审批闸门**（拦截）

删除、外发、部署、提权等高危动作必须二次确认或人工签核。

**实时熔断**（熔断）

出现异常链路、异常频率、异常目标时，立即终止执行。

### 第 4 层：安全执行环境

**沙箱运行时**（隔离）

执行发生在隔离环境，不直接操作宿主机系统。

**只读根文件系统**（文件）

关键路径不可写，系统级删除天然失效。

**临时凭证代理**（凭证）

按次签发、短时有效、范围受限，用完即失效。

**出站白名单**（网络）

只能访问允许的目标地址，防止数据外泄和任意外联。

### 危险路径示例：为何 `rm -rf /` ？败？

在 Harness 里，这不是“尽量避免”，而是被多层？

`rm -rf /`

1. **能力层先失败**  
   Agent 拿到的是“受限能力接口”，并没有“任意删除全系统”的能力描述。
2. **策略层直接拒绝**  
   系统级删除、根路径删除、递归破坏型操作命中禁止规则。
3. **审批层无法放行**  
   高危 destructive 动作需要额外授权；默认流程根本不会自动通过。
4. **运行时仍然做不到**  
   执行环境不绑定宿主根目录，关键文件系统只读，且没有高权限身份。
5. **审计与熔断同步触发**  
   危险请求被留痕、告警、阻断；必要时直接终止会话与回收凭证。

### 第 2 层：能力目录与最小权限 Harness

**能力注册表**（白名单）

只暴露可控能力：读文件、改局部代码、运行测试、生成补丁等。

**命令抽象化**（替代）

不用“任意 shell”，而是改成受限动作接口，减少危险表达空间。

**权限最小化**（最小化）

不给根权限，不给宿主写权限，不给长期密钥，不给默认外网通行证。

**作用域限定**（隔离）

仅允许访问指定工作区、指定仓库、指定分支、指定资源清单。

### Harness 安全护栏的五个落地原则

真正可靠的 Harness，不是“少犯错”，而是让高危越权动作在结构上没有成立条件。

**Agent 只提议**

把“决策”和“执行权限”拆开。

**能力先于命令**

优先暴露安全能力，而不是任意终端。

**最小权限默认**

不给就最安全，能少给绝不多给。

**沙箱强隔离**

就算想破坏，也破坏不到关键资产。

**审计可追责**

每一次越界尝试都能被看见、被阻断。

### 总结：Harness 如何“彻底杜绝” AI Agent 越权？

1. **不是告诉 Agent“别乱来”**  
   而是从系统设计上取消危险能力，让高危命令根本无法被有效表达。
2. **不是给一个万能终端**  
   而是只给有限、白名单、可审计的能力接口。
3. **不是相信模型会自律**  
   而是用策略网关、审批闸门、运行时隔离共同兜底。
4. **不是“发现坏事再补救”**  
   而是提前把宿主权限、根目录、长期密钥和任意外联通道全部锁死。

### Harness 安全护栏总架构

一条安全主线：任务输入 → 能力映射 → 策略裁决 → 审批拦截 → 沙箱执行 → 审计留痕。

Agent 只负责“提出意图”，真正能执行什么，由 Harness 决定。

- Agent 只能申请能力
- Harness 统一裁决
- 执行环境与宿主隔离
- 高危路径默认封死
- 结果可审计可回滚

#### 第 1 层：任务入口与意图收敛

**用户目标**（输入）

输入的是业务目标，而不是直接系统权限。

**任务边界**（约束）

限定仓库、目录、环境、资源范围，先把活动半径收紧。

**意图识别**（识别）

把“需求”翻译成可治理的能力请求，而不是原始命令流。

**风险分类**（分级）

区分只读、修改、外呼、删除、部署等不同风险等级。

### 第 5 层：可追责、可回放、可恢复

**全链路审计**（留痕）

记录谁发起、谁批准、执行了什么、访问了什么、结果是什么。

**执行回放**（回放）

能够重现决策链与执行链，便于课堂展示和事后复盘。

**回滚恢复**（恢复）

对可变更资源提供回滚路径，避免一次误操作造成永久损伤。

**紧急停机**（关闭）

一键断开会话、吊销凭证、冻结工具链，快速控制风险扩散。

### Harness 工具层 · 整体架构分层

六层纵深设计 · 从 Agent 大脑到真实世界执行

**Agent 决策层 · Brain**

推理规划、意图理解、工具需求生成。输出“需要调用什么工具、传什么参数”的结构化指令。

- 意图理解
- 任务拆解
- 工具决策

**Tool Router · 工具路由层**

接收 Agent 决策，匹配工具注册表，校验白名单权限，选择最优工具实例并路由到执行层。

- 工具匹配
- 白名单校验
- 实例路由

**Tool Registry · 工具注册中心**

统一存储所有工具的 Schema、版本、描述、参数约束、权限标签。支持热插拔，运行时动态注册 / 注销。

- Schema 管理
- 版本控制
- 热插拔
- 元数据索引

**Fault Governance · 异常治理层**

超时检测、自动重试（退避策略）、熔断保护、降级兜底。保障工具调用的韧性与稳定性。

- 超时控制
- 指数退避重试
- 熔断器
- 降级兜底

### 工具调用异常治理

超时 · 重试 · 降级 · 熔断 · 把微服务治理思想搬进 Agent 工具层

**超时控制**

为每个工具配置独立超时阈值，避免单个慢工具阻塞整个 Agent 推理链路。

分级超时：快（2s）/ 中（10s）/ 慢（30s）

**智能重试**

指数退避策略自动重试，区分可重试错误（网络抖动）与不可重试错误（参数非法）。

策略：1s → 2s → 4s，最多 3 次

**熔断保护**

连续失败达到阈值后自动熔断，进入冷却期。防止雪崩效应扩散到整条 Agent 任务链。

阈值：5 次失败 → 熔断 30s

**降级兜底**

工具不可用时切换到备用工具或本地缓存，保障 Agent 任务链路不中断，结果有据可循。

主工具熔断 → 自动切备用

流程：

1. Agent 发起：生成工具调用需求
2. 白名单校验：权限 & 阶段是否允许
3. 超时包裹：挂载独立超时计时器
4. 执行工具：实际调用外部能力
5. 失败重试：指数退避，最多 3 次
6. 熔断判断：累计失败是否触发
7. 降级兜底：备用工具或缓存结果
8. 链路上报：写入 Trace，指标统计

### Schema 设计规范

好 Schema vs 烂 Schema · 零歧义描述让模型理解准确率天差地别

**烂 Schema · 模型频繁误用**

- `name`：`"search"`  
  名称过于泛化，与其他工具区分度低，模型无法准确识别用途。
- `description`：`"搜索信息"`  
  描述极度模糊，缺乏使用场景、输入格式、返回格式说明。
- `parameters`：`{"query": {"type": "string"}}`  
  无约束条件：缺少长度限制、格式要求、枚举值、示例。
- `returns`：未定义  
  无返回值说明，模型不知道如何解析结果，二次调用出错率高。
- `errors`：未定义  
  无错误码映射，失败时模型无法判断是否应重试。

**好 Schema · 模型零歧义理解**

- `name`：`"web_search_v2"`  
  名称含模块前缀 + 版本，全局唯一，语义自解释。
- `description`：在互联网上检索最新信息，返回 top-N 结构化摘要。适用于：事实核查、新闻查询、技术文档检索。不适用于：私有数据库查询。  
  包含使用场景、适用边界、不适用场景，消除歧义。
- `parameters`：`query: string(10~200字符), lang: enum("zh","en"), top_n: int(1~10, default=5)`  
  明确类型、范围、枚举值、默认值，附带示例。
- `returns`：`Array<{title, url, snippet, score}>` · 按相关度降序排列  
  返回结构清晰，模型可直接解析使用。
- `errors`：429 限流重试，503 降级本地缓存，400 参数修正后重试  
  错误码与处理策略一一映射，Agent 自主容错。

### 工具注册 & 发现机制

让 Agent 清晰知道“能干什么”和“该干什么”

**工具注册表 · Registry**

| 工具 | 说明 | 状态 |
| --- | --- | --- |
| `web_search` | 联网检索，返回结构化摘要 · v2.1 | 正常 |
| `file_read` / `file_write` | 本地文件读写，支持路径沙箱 · v1.4 | 正常 |
| `code_exec` | 沙箱代码执行，Python / JS · v3.0 | 受限 |
| `db_query` | 只读数据库查询，SQL 注入防护 · v1.8 | 正常 |
| `send_email` | 邮件发送，需二次确认权限 · v1.2 | 正常 |
| `http_request` | 通用 HTTP 请求，URL 白名单过滤 · v2.0 | 已禁用 |

状态：正常 / 受限 / 已禁用

**工具发现流程 · Discovery**

1. **任务意图解析**  
   Agent 分析当前任务，提取所需能力关键词（如“搜索”、“写文件”、“执行代码”）。
2. **注册表语义匹配**  
   Tool Registry 按能力标签、描述向量相似度，检索候选工具集合。
3. **白名单权限过滤**  
   根据当前会话阶段、用户权限等级，从候选集中剔除不可用工具。
4. **Schema 注入上下文**  
   将可用工具的完整 Schema（名称、描述、参数约束）注入 Agent 上下文窗口。
5. **按需调用 & 结果回写**  
   Agent 按 Schema 规范调用工具，执行结果结构化后写回对话上下文。

### Schema 四项规范

**唯一性命名**

名称含模块前缀与版本号，全局唯一，杜绝工具混淆。

**边界清晰描述**

明确写出「适用场景」与「不适用场景」，缩小模型猜测空间。

**强约束参数**

每个参数附类型、范围、枚举、默认值及至少一个输入示例。

**返回值契约**

定义返回结构体、字段含义及错误码处理策略，形成完整契约。

核心结论：Schema 质量直接决定模型工具调用准确率。实测中，规范 Schema 相比模糊描述可将工具误用率降低 60% 以上。

### Harness 工具层 · 核心价值总结

六大工程能力 · 让 Agent 从“能用”走向“好用”再走向“可信”

**统一注册中心**（工程化管理）

所有工具在单一注册表中集中管理，Schema、版本、权限标签一体化存储，支持热插拔，运行时无感更新。

**语义工具发现**（智能调度）

Agent 无需“知道所有工具”，系统按任务意图自动检索最相关工具集并注入上下文，降低 Token 消耗。

**动态权限管控**（安全可控）

三维白名单（任务类型 × 会话阶段 × 权限等级）实时联动，高危工具零泄漏，安全边界清晰可控。

**零歧义 Schema**（质量保障）

规范的工具描述、参数约束、返回契约与错误码映射，让模型以极高准确率理解并使用每一个工具。

**微服务级治理**（高可用）

超时 / 重试 / 熔断 / 降级形成完整容错闭环，将微服务韧性工程思想完整移植到 Agent 工具调用层。

**全链路可观测**（数据驱动）

每次工具调用全程 Trace，耗时、成功率、失败原因实时上报，为持续优化提供数据驱动的决策基础。

Harness 工具层的本质：不是在 Agent 和工具之间加一层“包装”，而是构建一套完整的工具操作系统——让 Agent 知道能做什么、该做什么、怎么安全地做、出错了怎么恢复。这才是从 Demo 走向生产级 Agent 系统的关键工程跨越。

### Tool ≠ Function Call

裸调用 vs Harness 工具层 · 差了整整一个工程维度

**裸 Function Call**

- 硬编码函数签名，模型直接裸调，无任何元数据描述。
- 无权限控制，任何阶段可调用任意工具。
- 调用失败直接抛错，无重试 / 降级机制。
- 描述模糊，模型频繁误用工具或参数填错。
- 无日志、无追踪，问题排查全靠猜。
- 工具集固定，无法按任务动态切换。

**Harness Tool Layer**

- 统一注册中心，工具具备完整 Schema、版本、分类元数据。
- 动态白名单，按任务类型 / 阶段 / 权限精细管控。
- 超时重试 + 熔断降级，调用具备完整容错闭环。
- 零歧义 Schema 规范，模型理解准确率显著提升。
- 全链路 Trace，每次调用可观测、可回溯。
- 热插拔工具集，运行时动态注册 / 注销无需重启。

核心洞察：Tool Layer 不是“给模型加几个函数”，而是一套完整的工具生命周期管理体系——从注册、发现、调度到治理，每一环都有工程保障。

### 工具集成层

#### 在 Harness 工具层里，两类风险是怎么被截断的？

**参数带毒 / 注入风险**

Agent 传入危险参数

- Harness 工具层先做 Schema 校验与规则匹配
- 禁止自由 SQL 拼接
- 只允许参数化模板执行
- 异常时返回统一安全错误

**调用越权 / 数据越界**

Agent 试图调用高权限工具或查询超范围数据

- Harness 先做工具白名单与身份鉴权
- 再自动追加租户 / 用户范围条件
- 越权直接拒绝，结果也不会外泄

**Harness 工具层的关键部件**

- **工具目录**：把 Harness 可调用工具登记清楚，再决定 Agent 能看到什么。
- **权限控制器**：在 Harness 中根据身份、角色、上下文决定能不能调。
- **参数校验器**：在 Harness 中校验入参结构、类型、边界和值域。
- **异常兜底器**：统一拦截报错、净化异常、保护内部细节不外泄。

**Harness 统一输出结构示例**

```json
{
  "status": "ok",
  "source": "harness_tool_layer",
  "data": [
    {"id": 101, "name": "****", "amount": 1280}
  ],
  "meta": {"tool": "db_query_readonly", "rows": 1},
  "safety": {"masked": true, "fallback": true}
}
```

#### 总结：Harness 工具层到底做了什么

先拦截，再执行，最后兜底。

面试回答可直接落在这四点：

1. 在 Harness Engineering 中，工具集成层不是简单转发，而是整个工具调用的安全入口。
2. **权限控制**解决“这个工具能不能调、这份数据能不能查”的问题。
3. **参数校验**解决“传进来的参数是不是安全、是不是合规”的问题。
4. **异常兜底**解决“执行失败怎么办、报错能不能安全返回、结果要不要脱敏”的问题。

在 Harness Engineering 里，真正关键的不是让 Agent“会调工具”，而是让 Harness 工具层把每一次调用都变成有权限边界、有参数约束、有异常兜底的安全调用。

#### Harness 工具集成层总览

上半段：Harness 如何决定“能不能调、怎么调”

1. **Agent 发起工具请求**（调用入口）  
   - Agent 提出“调用数据库查询工具”的意图  
   - 请求先进入 Harness Engineering 的工具集成层  
   - Agent 不能直接连数据库，只能过 Harness 工具层  
   - 用户身份、会话上下文、租户信息
2. **Harness 工具目录**（Harness 工具注册与发现）  
   - Harness 统一登记工具名、能力描述、参数 Schema、权限级别  
   - 只把允许暴露的工具提供给 Agent 发现  
   - 查询类工具、敏感类工具在 Harness 中分级管理  
   - 标准化注册、白名单发现、能力分级
3. **权限控制 + 参数校验**（Harness 调用前拦截）  
   - Harness 先判断：当前身份是否有权调用该工具  
   - 再校验：参数类型、长度、枚举、必填项是否合规

   - 发现危险字段、越权范围、异常条件时直接拒绝  
   - 权限过滤、Schema 校验、参数消毒

下半段：Harness 如何做到“安全执行、异常兜底”

4. **沙箱执行层**（Harness 受控执行）

   - 限制网络、文件、系统命令、CPU / 内存 / 时长  
   - 单次调用单次环境，避免风险扩散到外部系统  
   - 进程隔离、资源收敛、执行边界
5. **受控数据访问层**（Harness 数据访问适配）

   - 最小权限、范围注入、错误隐藏
6. **异常处理 + 结果净化**（Harness 调用后兜底）  
   - Harness 将结果统一格式化，便于下游继续处理  
   - 对敏感字段做断、对返回条数做限制、对异常信息做净化  
   - 保留审计日志，记录谁调了什么工具、查了哪些范围

**核心理解**

### 权限、安全与行为边界 / 从单次回答转向持续调度 / 验证、反馈与自动修正

**护栏层 · 风险控制：权限、安全与行为边界**

系统能做什么、不能做什么，在运行前就被严格定义。

- **权限最小化**：按任务开放最少资源，避免越权。
- **沙箱隔离**：高风险操作在受限环境中进行。
- **敏感动作确认**：删除、改写、外发前设置检查点。
- **审计留痕**：每一步可追踪、可回放、可复盘。

**中枢层 · 驾驭核心**

驾驭中枢：推理 / 决策 / 编排

从单次回答，转向持续调度。

中枢接收目标、上下文与资源，在护栏限制下决定下一步：检索、调用工具、生成结果、发起验证，或回退重试。

- 判断当前最合适的动作
- 失败时进入修正回路，而不是直接结束
- 管理状态切换：开始 → 执行 → 校验 → 交付

**闭环层 · 质量保证：验证、反馈与自动修正**

输出结果先经过检查与回流，再决定是否进入交付阶段。

- **规则校验**：格式、字段、约束是否满足要求。
- **测试验证**：针对任务结果执行检查或样例测试。
- **自动重试**：失败后带着原因再次修正输出。
- **人在回路**：关键节点由人工确认最终动作。

### 总设计纲要拆解

#### Agent 专业化（Agent Specialization）

核心原则：专注于特定领域、拥有受限工具的 Agent 优于拥有全部权限的通用 Agent。

Carlini（Anthropic C 编译器项目）将 Agent 专业化为编译器核心、去重、性能优化和文档四类角色。

Vasilopoulos 部署了 19 个领域特定 Agent。

Huntley 使用子 Agent 来保持主 Agent 上下文的清洁。

专业化不仅是组织性的——它本身就是上下文管理策略。每个专家因为携带更少的无关信息，所以运行在 "Smart Zone" 内。

**实践中的角色分工：**

| Agent 角色 | 职责范围 | 工具权限 |
| --- | --- | --- |
| 研究 Agent | 探索代码库、分析实现细节 | 只读（Read, Grep, Glob） |
| 规划 Agent | 将需求分解为结构化任务 | 只读，无写入权限 |
| 执行 Agent | 实现单个具体任务 | 限定范围的读写权限 |
| 审查 Agent | 审计完成的工作，标记问题 | 只读 + 标记权限 |

#### 熵管理（Entropy Management）——垃圾回收

随着时间推移，软件系统会逐渐混乱（熵增），技术债务会积累。OpenAI 采用持续小额偿还的策略，而不是等问题严重时集中处理——他们把这个方法形象地称为垃圾回收，并认为技术债务就像高息贷款。

具体措施：定期运行后台 Codex 任务扫描偏差、更新质量等级、发起针对性重构 PR。此外还有一个专门的 Doc-gardening Agent（文档园丁代理），在后台自动扫描文档与代码之间的不一致，发现过时内容就自动提交 PR 修复——Agent 为 Agent 维护文档。

#### 架构约束（Architecture Constraints）——缰绳

OpenAI 团队建立了严格的层级依赖模型：

`Types → Config → Repo → Service → Runtime → UI`

下层不能反向依赖上层。所有架构规则被编码为自定义 Linter 规则，违反即 CI 阻止合并——无论代码是人写的还是 AI 写的。

有个关键细节：Linter 的错误信息本身也是上下文工程。它不只说你违反了规则 X，而是解释为什么这个规则存在、正确做法是什么，这样 Agent 读到错误后就能自我理解并修正，不需要人类介入。

#### 反馈循环（Feedback Loop）——智能体审智能体

传统开发中，人类工程师负责代码审查（Code Review）。在驾驭工程中，这个工作变成了智能体对智能体的方式：Codex 在本地审核自身更改，请求额外审查，循环往复直到通过。

反馈循环中的钩子可以运行预定义的测试套件，并在失败时带着错误信息循环回到模型，或者提示模型独立评估其代码。如果 AI 写的测试用例通过了带有 Bug 的代码，Harness 就会判定测试无效，强迫它重新思考测试边界。

#### 持久化记忆（Persistent Memory）

核心原则：进度持久化在文件系统上，而非上下文窗口中。每次新 Agent 会话从零开始，通过文件系统制品重建上下文。

Anthropic 解决这一问题的方案堪称经典：

**初始化 Agent**：首次会话使用专门的 prompt，要求模型建立初始环境——`init.sh` 脚本、`claude-progress.txt` 进度文件和初始 git 提交。

**编码 Agent**：后续每次会话要求模型在做出增量进展的同时，留下结构化更新。

每个编码 Agent 的典型会话启动流程如下：

1. 运行 `pwd` 查看工作目录
2. 读取 `git log` 和进度文件，了解最近的工作
3. 读取 feature list 文件，选择最高优先级的未完成功能
4. 启动开发服务器，运行基础端到端测试
5. 确认基本功能正常后，开始新功能开发

关键发现：使用 JSON 格式追踪 feature 状态比 Markdown 更有效，因为 Agent 不太可能不恰当地修改或覆盖结构化数据。

#### 结构化执行（Structured Execution）

核心原则：将思考与执行分离。研究和规划在受控阶段进行，执行基于验证过的计划，验证通过自动化反馈（测试、Linter、CI）和人类审查完成。

所有团队都施加了刻意的执行序列：理解 → 规划 → 执行 → 验证。

OpenAI 使用声明式 prompt 和反馈回路。轻量的计划用于小变更，复杂工作通过带有进度和决策日志的执行计划完成，并检入仓库。

Huntley 将规划模式与构建模式分离。

Horthy 的 Research-Plan-Implement 工作流围绕上下文管理精心设计。

人工检查点的价值：审查计划远比审查代码快。当规格正确时，实现自然可靠。当规格有误时，可以在 500 行代码生成之前及时纠正。

#### 上下文工程（Context Engineering）——新员工手册

就像给新员工一本详细的工作手册，`AGENTS.md` 是 AI 智能体进入代码仓库时看到的第一份指南。但这不是一本静态的 1000 页说明书——上下文是稀缺资源，过多的指导反而会挤掉任务、代码和相关文档的空间，变成陈旧规则的坟场。

更好的做法是：提供一个稳定、小巧的入口点，然后教 Agent 根据当前任务按需检索和拉取更多的上下文。Mitchell Hashimoto 的 Ghostty 项目 `AGENTS.md` 里每一行都对应一个历史 Agent 失败案例——文档是活的反馈循环，不是静态制品。

核心原则：Agent 应当恰好获得当前任务所需的上下文——不多不少。

每个团队都独立发现，将所有指令塞进一个文件无法扩展。解决方案是分层上下文与渐进式披露：

- OpenAI 使用 `AGENTS.md` 作为动态反馈循环文件，每当 Agent 遇到失败时更新。
- Anthropic 使用大量 README 和每次会话频繁更新的进度文件。
- Horthy 倡导“频繁有意识压缩”（Frequent Intentional Compaction）。
- Vasilopoulos（2026 论文）将上下文形式化为三层：热记忆（Hot Memory）、领域专家（Domain Experts）、冷记忆知识库（Cold-Memory Knowledge）。

### Agent Harness架构解析

#### 落地难点与 Harness 解决方案

**难点 1：多 Agent 状态不一致**（并发冲突）

分布式环境下，多个 Agent 同时读写共享环境，极易产生竞态条件。

驾驭方案：引入分布式数据库的时空一致算子（Vector Clock），确保逻辑时间轴上的状态绝对同步。

**难点 2：幻觉的级联放大**（容错灾难）

在上游节点微小幻觉，会被下游 Agent 放大为业务故障。

驾驭方案：部署门控巡检架构（Gated Inspection）。强制插入轻量级校验 Agent，实现强？致性的自我纠错闭环。

**难点 3：算力与合规的矛盾**（数据主权）

大模型在云端，但企业业务数据需要本地化处理以满足合规要求。

驾驭方案：依托混合网格化（Hybrid Mesh），算力密集的规划在云端，涉及隐私的动作执行在边缘节点。

#### 三个基础组件

- 时空一致性同步（Vector Clock）
- 异步消息总线（Event Queue）
- 分布式长期记忆（Vector DBs）

### Harness Agent 记忆三层模型

Harness 将 Agent 记忆按时间维度拆分为三层，每层解决不同生命周期的状态保持问题，层间通过统一接口协议流转数据。

**工作记忆**（Working Memory）

即时 · 易失

- 当前任务
- Token 窗口
- 单步有效
- 实时更新

**会话记忆**（Session Memory）

跨轮 · 半持久

- 多轮对话
- 中间状态
- 上下文锚点
- 会话内共享

**长期记忆**（Persistent Memory）

跨会话 · 持久

- 用户偏好
- 知识沉淀
- 历史经验
- 永久有效

### 上下文压缩技术

Token 窗口是稀缺资源，压缩的本质是：在有限空间内保留最高信息密度，让 Agent 始终“记得最重要的事”。

**Harness 压缩管线流程**

1. **原始上下文注入**  
   System Prompt + 历史对话 + 工具结果 + 用户输入，原始 Token 可能超出窗口上限。
2. **重要性评分**  
   对每个 chunk 打分：相关性 × 时效性 × 稀有性，低分内容优先裁剪。
3. **摘要折叠**  
   对超出窗口的历史段落调用轻量摘要模型，生成压缩摘要替代原文。
4. **滑动窗口裁剪**  
   保留最近 N 轮原始对话 + 前序摘要，确保总 Token ≤ 目标上限。
5. **压缩后上下文输出**  
   最终送入 Agent 的上下文：精简但高密度，关键信息无损保留。

**摘要策略 · Summarization**

对超龄历史内容调用轻量模型进行“有损压缩”，保留语义骨架，丢弃冗余细节。适合对话轮次长、重复信息多的场景。

- 渐进摘要
- 分段折叠
- 层级聚合

**重要性排序 · Importance Ranking**

基于相关性评分对上下文片段排序，优先保留与当前任务强相关的内容，低相关度片段自动淘汰，实现语义级精准裁剪。

- TF-IDF 相关性
- 向量相似度
- 时效衰减

**滑动窗口裁剪 · Sliding Window**

维护一个固定大小的滑动窗口，最新 N 轮对话始终保留原文，窗口外的内容转换为摘要或直接丢弃，兼顾时效性与连贯性。

- 固定轮次窗口
- Token 预算控制
- 动态步长

### 窗口容量对比示意

- 压缩前：历史对话 × 32 轮（溢出）
- 压缩后：摘要 + 近 6 轮原文 + 当前输入

### 状态管理三大模式

Harness 中 Agent 状态管理没有银弹，根据任务复杂度与可恢复性要求选择合适的模式是关键工程决策。

**Checkpoint-Resume**（检查点 · 断点续跑）

在任务执行关键节点快照完整状态，异常中断后可从最近检查点无损恢复，无需重头执行。

- 定义检查点触发时机（步骤 / 时间 / 事件）
- 序列化 Agent 完整状态快照至持久层
- 故障检测后自动加载最近可用快照
- 从断点位置继续执行，跳过已完成步骤

高可恢复性、节省重复计算、长任务必备。

**事件溯源**（Event Sourcing · 全量事件日志）

不直接存储当前状态，而是记录所有状态变更事件，任意时刻的状态均可通过重放事件流推导出来。

- 每次状态变更产生一个不可变事件记录
- 事件追加至持久化事件日志（Append-Only）
- 当前状态 = 重放全量或增量事件流
- 支持时间回溯、审计与调试

完整可审计、支持时间回溯、调试友好。

**有限状态机**（Finite State Machine · FSM）

将 Agent 任务流程显式建模为有限个状态与合法转移规则，状态转移有据可查，异常行为可拦截。

- 枚举所有合法状态节点
- 定义状态转移条件与触发事件
- 运行时校验每次转移是否合法
- 非法转移触发异常处理或人工介入

状态：初始化 → 执行中 → 等待 → 完成

行为可控、异常可拦截、逻辑清晰。

### 三层记忆对比

**工作记忆**（Working Memory）

- 作用范围：单次推理步骤内的即时上下文
- 生命周期：任务完成即清空，高度易失
- 容量限制：受 Token 窗口硬性约束
- 典型内容：System Prompt、当前指令、工具调用结果、推理链

**会话记忆**（Session Memory）

- 作用范围：同一会话内跨轮次状态保持
- 生命周期：会话结束后可选择久化或丢弃
- 容量限制：受压缩策略动态调控
- 典型内容：对话历史摘要、任务进度、中间变量、用户意图

**长期记忆**（Persistent Memory）

- 作用范围：跨会话的知识沉淀与个性化偏好
- 生命周期：持续有效，主动写入 / 遗忘机制管理
- 容量限制：存储层无上限，检索时按需召回
- 典型内容：用户画像、领域知识库、历史偏好、项目背景

### 存储方案：三种路线的适配分析

没有万能的存储方案，Harness 根据记忆类型、查询模式与数据结构特征进行分层选型。

**向量数据库**（Vector Database）

- 核心能力：语义相似度检索 · 模糊匹配
- 数据形态：非结构化文本 → Embedding 向量
- 查询方式：ANN 近似最近邻 · cosine 相似度
- 最佳场景：知识库召回、对话历史检索、语义搜索

**图数据库**（Graph Database）

- 核心能力：关系推理 · 多跳路径查询
- 数据形态：实体 + 关系 → 知识图谱
- 查询方式：图遍历 · 路径匹配 · 子图查询
- 最佳场景：实体关系推理、知识图谱、依赖分析

**结构化存储**（Structured Storage）

- 核心能力：精确查询 · 事务一致性
- 数据形态：结构化字段 → 表 / KV / 文档
- 查询方式：SQL / KV Lookup · 精确索引
- 最佳场景：用户画像、Agent 配置、任务状态

### 三大高频陷阱与解法

Harness 落地记忆系统过程中反复踩坑的典型案例，每一条都是真实付出代价换来的工程经验。

**陷阱 #01 记忆污染**（Memory Pollution）

错误信息、过期数据或噪声片段被持久化写入长期记忆，导致后续所有会话都受到污染，Agent 持续输出错误结论，且问题随时间累积愈发严重，极难溯源。

解决方案：

- 写入前置验证：置信度阈值过滤，低质量内容拒绝写入
- 记忆隔离机制：用户 / 任务维度命名空间隔离，防止跨污染
- TTL 过期策略：为记忆条目设置有效期，自动淘汰过期数据
- 人工审核通道：高风险写入触发人工 Review 流程

**陷阱 #02 上下文漂移**（Context Drift）

多轮对话中 Agent 的关注焦点随对话历史逐渐偏离原始目标，经过十几轮交互后，Agent 已完全忘记初始任务意图，每一步看似合理，整体却南辕北辙。

解决方案：

- 目标锚点注入：将初始任务目标固定在 System Prompt 中，每轮强制携带
- 定期目标对齐检查：每 N 轮触发一次意图一致性校验
- 检查点状态快照：关键节点保存完整目标状态，发现漂移立即回滚
- 会话摘要强制包含原始目标，压缩时目标字段不可裁剪

**陷阱 #03 幻觉记忆**（Hallucinated Memory）

Agent 自信地“回忆”起从未发生过的事件或从未存储的信息，将模型生成内容误认为真实记忆，并基于此做出决策，是记忆系统最隐蔽、危害最大的故障模式之一。

解决方案：

- 记忆来源标注：每条记忆条目强制关联来源 ID 与时间戳
- 召回时交叉验证：检索结果与原始存储 hash 比对，发现篡改
- 生成 vs 检索分离：明确区分“模型生成内容”与“存储检索内容”
- 不确定性声明：无法找到真实记忆时，强制输出“未知”而非捏造

- **三层记忆架构**：工作 / 会话 / 长期，按时间维度分层治理

- **长流程任务**（长链路）：测试多阶段规划、挂起恢复、跨步骤记忆保持，以及中间验证的连贯性。
- **故障注入**（稳定性）：模拟工具超时、检索失败、网络抖动、上下文截断，评估退化运行与恢复能力。
- **对照放量**（线上灰度）：小流量对比新旧 Harness，在真实环境下衡量成功率、延迟、成本与风险变化。

### 调优闭环与典型优化动作

**调优闭环**

1. **定位瓶颈**  
   先用轨迹与指标判断问题发生在上下文、工具、编排、验证还是发布门禁，而不是盲目整体调参。
2. **拆解原因**  
   把失败任务按模式分类：信息不足、步骤漂移、工具选错、验证误杀、超时、成本失控、恢复失败。
3. **改 Harness 结构**  
   优先优化上下文裁剪、工具门控、缓存策略、重试上限、终止条件、验证规则、回滚路径。
4. **对比实验**  
   用同一批基准任务和同一预算约束做 A/B 对比，确保性能提升不是以安全、成本或稳定性为代价。
5. **回归门禁**  
   把通过验证的新策略写入版本门禁，形成可持续复用的 Harness 性能资产。

**典型优化动作**

- **上下文减脂**：压缩无关信息，提高命中率，降低长上下文带来的延迟与噪声干扰。
- **工具路由收敛**：减少错误工具选择和无效调用，优先把工具成功率做高。
- **验证器分层**：先轻量初筛，再做关键验证，平衡验证精度与验证开销。
- **重试策略控速**：限制盲目重试，基于错误类型做差异化恢复，避免成本雪崩。
- **缓存与复用**：复用稳定中间结果，减少重复计算、重复检索和重复工具执行。
- **灰度发布门禁**：小流量验证改动收益，达标再放量，不让局部优化演变为线上回退。

### 总结：Harness 性能，不是单点速度，而是系统闭环能力

1. **先定标准，再谈优化**  
   企业级 Harness 必须先定义“什么叫成功”，否则任何性能提升都难以解释、更难以复现。
2. **基准测试要贴近真实任务**  
   离线任务集、真实回放、故障注入、长链路与灰度对照，缺一项，评估都容易失真。
3. **持续调优的重点在 Harness**  
   真正决定系统表现的，往往是上下文管理、工具治理、编排规则、验证器和回滚机制。

一句话带走：衡量 Harness，不是问“它会不会做”，而是问“它能不能稳定、经济、安全地把任务做成，并且越跑越好”。

## Harness状态管理

### 记忆读取 · 当前工作集 · 状态写回

**记忆读取**

按需读取，不全量灌入；只取和“当前动作”最相关的状态片段。

**当前工作集**

当前阶段目标 + 最近摘要 + 必要历史 + 当前环境观察。

**状态写回**

执行后把新结论、新工件、新风险、新计划回写到 Harness 状态层。

**Checkpoint 快照仓**

在“完成阶段 / 达到里程碑 / 即将中断 / 高风险动作前后”生成进度快照。

- 保存：当前阶段、已完成项、待办、关键工件引用、错误上下文
- 好处：崩溃后可恢复、跨天可续跑、多人 / 多 Agent 可交接
- 形式：结构化状态 + 摘要 + 事件偏移量 + 关键资源句柄

**时序控制器**

控制何时继续、何时等待、何时重试、何时结束。

- 休眠等待
- 定时唤醒
- 重试退避
- 阶段切换

**恢复器 / 读档器**

新会话启动时，先加载最新可用 checkpoint，再重建工作内存，继续推进任务。

- 找到最近有效快照
- 重建当前工作集
- 从断点继续执行

### 一句话总结 Harness 的状态管理思路

长周期任务的关键，不是让 Agent 永久在线，而是让状态永久可用。Harness 通过“分层记忆 + checkpoint + 调度恢复”三件事，把一次会话能力，变成可跨天、可追踪、可恢复的任务能力。

- **记忆分层**：工作内存负责当下，会话内存负责本轮，长期记忆负责跨天与跨阶段沉淀。
- **快照存档**：在关键节点保存 checkpoint，让任务可以暂停、崩溃恢复、多人交接。
- **时序控制**：用调度器决定何时继续、何时等待、何时重试，真正把 Agent 变成长期运行系统。

### Harness 里，最值得被显式保存的状态

真正决定“能不能恢复”的，不是聊天记录有多长，而是状态对象是否完整、结构是否稳定。

- **目标状态**：总目标、阶段目标、验收标准、当前优先级。
- **任务树**：已完成、进行中、阻塞中、待开始的子任务结构。
- **工件引用**：文档、文件、结果、代码片段、资源路径与版本。
- **风险与异常**：失败原因、重试次数、待确认问题、回滚点。
- **下一步动作**：下一次唤醒后第一步该做什么，避免“重新思考一遍”。
- **时序元数据**：休眠截止、下次触发条件、超时阈值、重试策略。
- **约束与权限**：允许做什么、不允许做什么、预算和边界条件。
- **Checkpoint 标识**：最近快照编号、事件偏移、恢复入口与一致性校验。

### Harness Runtime Core

状态装配 + 时序控制 + 护栏治理

**输入侧**

- **任务目标**：总目标、阶段目标、验收标准
- **外部事件**：新消息、文件变更、定时触发、人工干预
- **约束条件**：权限范围、预算上限、时间窗口、风险边界

**运行核心**

- **状态装配器**：按任务阶段把工作内存、会话内存、长期记忆拼成“当前工作上下文”。
- **状态对象**：维护任务树、阶段、工件、风险、下一步、最近 checkpoint 等核心字段。
- **调度器**：负责休眠、唤醒、重试、延迟执行、等待外部条件满足。
- **护栏与验证**：约束工具使用、校验结果质量、拦截高风险动作。
- **摘要压缩器**：把冗长历史转成结构化摘要，避免上下文膨胀。
- **事件记录器**：把关键动作写入事件流，便于追踪、回放与恢复。

核心原则：不是“永远在线记住一切”，而是“每轮只加载必要状态，完成后再写回状态”。

**执行闭环**

- **计划**：拆解下一步，选择合适策略与工具
- **执行**：调用工具、读写文件、查询数据、操作系统资源
- **观察**：收集结果、异常、日志、外部反馈
- **验证**：判断是否完成、是否回滚、是否进入下一阶段

### Harness：让 Agent 记住一项会持续很多天的任务

Harness · 2026 年 2 月开始被系统化讨论的开发范式

关键不在“把全部历史塞进上下文”，而在于：把状态分层管理，把执行过程事件化，把阶段进度做成 checkpoint，这样任务可以像“存档 / 读档”一样安全延续。

- 工作内存
- 会话内存
- 长期记忆
- Checkpoint
- 时序控制
- 中断恢复

- **目标不会丢**：任务目标、阶段目标、约束条件被显式写入状态对象。
- **进度可存档**：每到关键节点自动生成 checkpoint 快照。
- **历史被压缩**：不把所有对话硬塞给模型，而是摘要、抽取、结构化。
- **下班也能续上**：会话结束后保存状态，下一次加载快照继续推进。

### 中断恢复：Harness 如何像“游戏存档”一样续上任务

会话结束不等于任务结束。Harness 把“对话”与“任务状态”拆开：对话可以终止，任务可以继续。

1. **到达中断点**  
   阶段完成、人工离开、资源不足、等待外部条件。
2. **写入快照**  
   把当前阶段、关键结果、下一步动作写成 checkpoint。
3. **进入休眠**  
   释放会话上下文，只保留持久状态与事件记录。
4. **触发唤醒**  
   次日恢复、定时触发、人工继续、外部事件到达。
5. **加载快照**  
   恢复最近有效 checkpoint，并重新构建工作内存。
6. **断点续跑**  
   从“下一步动作”直接开始，而不是从头回顾全部历史。

# ClaudeCode源码架构剖析

## ReAct 循环引擎 · Agent 的「心跳」

中心：**Agent Loop**

- ReAct 范式
- 无外部框架依赖
- 纯手工实现

| 步骤 | 内容 |
| --- | --- |
| ① 输入感知 | 接收用户指令 + 加载上下文；CLAUDE.md + 历史对话 |
| ② 提示构建 | 动态拼装系统提示词；注入工具定义 + 权限规则 |
| ③ 模型推理 | 调用 Claude API；流式接收 reasoning + 决策 |
| ④ 工具调用 | 并行/串行执行 40+ 工具；`defer_loading` 懒加载优化 |
| ⑤ 权限校验 | 四层权限链实时拦截；危险操作触发用户确认 |
| ⑥ 结果持久 | 工具结果 + 对话写回磁盘；Prompt Cache 分段缓存 |

### 多 Agent 协作：Coordinator + Sub-Agent 模式

主模型（Coordinator）负责任务拆解与调度，将复杂子任务分发给 Sub-Agent（teammate / fork / built-in / background / remote），每个 Sub-Agent 独立持有上下文，完成后汇报结果。这是 Claude Code 能处理大型工程项目的根本原因。

## 事件始末 · 一次 npm 配置失误引发的「最佳开源」

| 时间 | 事件 | 说明 |
| --- | --- | --- |
| T+0 min | v2.1.88 发布 | Anthropic 推送 npm 包，含 `cli.js.map` 未被清除 |
| T+23 min | 异常发现 | 安全研究员寿超鹏注意到包体积异常膨胀 |
| T+45 min | 全网扩散 | 逆向工具运行 1906 个 TS 文件，完整还原源码，上传 GitHub |
| 当日内 | 4.1 万次 Fork | GitHub 仓库被 fork 超 41,500 次，覆盖全球开发者 |
| 随后 | Anthropic 响应 | 发布补丁版本，移除 sourcemap，承认配置失误 |

### 根本原因

构建脚本未在 `.npmignore` 中排除 `*.map` 文件，sourcemap 被完整打包进生产 npm 包，无混淆、无加密。

### 泄露价值

完整 TypeScript 源码：系统提示词、工具定义、权限逻辑、Agent 编排系统、记忆管理机制，堪称「工业级 Agent 开发教材」。

### 技术意义

首次让外界看到一个无框架依赖的顶级 Agent 是如何从零构建的，证明「护城河在工程，不在模型」。

## 四层权限链 · 安全与效率的平衡艺术

企业级策略 → 项目级规则 → 用户级偏好 → 工具级默认

| 层级 | 说明 |
| --- | --- |
| 企业级策略 | Operator 全局配置文件定义组织级权限边界 |
| 项目级规则 | CLAUDE.md 中项目特定权限；白名单/黑名单 |
| 用户级偏好 | 运行时用户交互确认；记住本次选择 |
| 工具级默认 | 每个 Tool 内置默认权限策略；只读 vs 写入 |

### 白名单操作（自动放行）

只读操作（Read / LS / Grep）在信任目录内自动执行，无需确认，保持流畅度。

### 写入/网络操作（交互确认）

文件写入、网络请求等操作显示 diff 预览，用户确认后执行，支持「本次允许/永久允许」。

### 危险操作（强制拦截）

删除系统文件、访问 `~/.ssh`、修改 `/etc` 等操作被硬编码拦截，任何配置均无法绕过。

### 核心设计亮点

每个 Tool 含 `defer_loading: true` 属性实现懒加载，减少上下文占用；工具注册、描述、参数校验、调用分发全部手工实现，零 LangChain 依赖。

### 并行工具调用

支持多工具并行执行；所有工具调用结果（包括 Read / Bash / Grep 的输入输出）完整写入本地磁盘，形成可审计的完整执行轨迹。

## Harness Engineering · Claude Code 印证的新范式

### 传统开发范式（Prompt Engineering）

- 人工编写代码：工程师是主要代码生产者
- AI 作为辅助工具：补全、建议，被动响应
- 逐步提示优化：反复调整 prompt 换取更好结果
- 依赖框架封装：LangChain/LangGraph 等抽象层

### Harness Engineering

- 人掌舵 · Agent 执行：工程师设计「赛道」，Agent 跑步
- 构建运行环境：工具集、约束系统、反馈回路
- 闭环自动验证：测试通过、构建成功才算完成
- 零框架手工构建：Claude Code 印证：直接掌控更可靠

### 上下文工程

精心设计每次进入 Agent 的信息结构，是 Harness 的核心竞争力。

### 工具约束设计

不优化模型，优化模型运行的「环境」和可用工具边界。

### 反馈回路闭环

测试结果、构建日志、lint 输出自动反馈给 Agent，形成自愈循环。

### 可观测 & 审计

每一步操作可追溯，是企业级可信 Agent 的必要条件。

## 刹车系统

### 从 Claude Code 源码泄露看到 Agent 的“刹车系统”

让 Agent 不乱来，核心不是“更聪明”，而是把权限分层、把高危动作卡住、把执行环境关进沙箱、把结果全程留痕。

标签：默认拒绝、最小权限、风险分级、关键动作确认、沙箱隔离、审计回滚。

#### Agent 不乱来，需要这 4 块一起工作

权限控制架构

| 块 | 说明 |
| --- | --- |
| 目标先收口 | 先限定任务边界、身份、工作目录、上下文来源，不让意图无限扩张。 |
| 工具再放权 | 工具白名单 + 参数校验 + 命令规范化，不让模型自由拼接危险动作。 |
| 执行有护栏 | 沙箱、路径边界、网络开关、密钥隔离，把副作用困在受控环境里。 |
| 结果能追能撤 | 日志、Diff、告警、回滚点，让每一步都可追踪、可审计、可恢复。 |

### Agent 权限控制的真正重点：每一步都要有“闸门”

不是让模型“自己判断是否安全”，而是把任务入口、策略判断、执行过程、结果闭环拆成多道独立防线。

风险类型：上下文投毒、权限漂移、工具越权、自循环失控、外部连接扩散。

| 步骤 | 名称 | 说明 | 要点 |
| --- | --- | --- | --- |
| 01 | 入口收敛 | 先定义“谁在发起、要做什么、能看哪些上下文、允许碰哪些目录”，把任务范围锁小。 | 身份绑定、任务范围、工作目录、上下文清洗、只读优先 |
| 02 | 策略判定 | 把“是否能做”从模型本身剥离出来，交给独立的权限与策略层统一判断。 | 工具白名单、Schema 校验、命令规范化、风险分级、默认拒绝 |
| 03 | 执行护栏 | 即使策略放行，也不代表直接裸奔执行；真正落地前，环境层还要再做一轮限制。 | 沙箱隔离、路径边界、密钥隔离、网络开关、人工确认 |
| 04 | 结果闭环 | 让每次操作都留下证据：改了什么、调用了什么、能否回滚、出了问题怎么追责。 | 操作日志、Diff 审计、告警联动、回滚点、可观测性 |

### 低 / 中 / 高风险动作

| 级别 | 说明 | 例子 |
| --- | --- | --- |
| 低风险动作 | 只读查询、搜索、读文件、代码理解、日志分析，可自动执行，但仍需留痕。 | 读文件、搜索、分析 |
| 中风险动作 | 改代码、写配置、安装依赖，可以放权，但要受目录、配额、策略和审计共同约束。 | 改代码、写配置、装依赖 |
| 高风险动作 | 删文件、执行 Shell、发消息、联网与外部系统，必须二次确认，必要时直接拒绝。 | 删除、Shell、外联、对外发送 |

### 让 Agent 不乱来的 6 层权限护栏

权限控制不是一个“开关”，而是一套层层递进的约束系统；前一层放过了，后一层还能继续拦。

| 层 | 名称 | 说明 |
| --- | --- | --- |
| 01 | 目标边界 | 限定当前任务、当前用户、当前会话，不允许模型自行扩展目标，更不允许“顺手多做一点”。 |
| 02 | 工具边界 | 默认 deny，按场景开白名单；读、写、执行、联网、MCP、Hook 不同能力必须分别控权。 |
| 03 | 参数边界 | 参数必须结构化校验；路径、命令、模式、目标对象都要被模板化与正规化，避免绕过。 |
| 04 | 环境边界 | 执行必须在受控环境里：目录隔离、网络开关、密钥隔离、资源配额、临时工作区。 |
| 05 | 决策边界 | 按风险分级授权：低风险自动，中风险受策略限制，高风险必须人工确认或直接阻断。 |
| 06 | 结果边界 | 所有副作用都要留痕：日志、Diff、告警、审计记录、回滚点，确保事后能查、能撤、能追责。 |

### 7 个关键词，构成 Agent 的“刹车系统”

| 关键词 | 说明 |
| --- | --- |
| 默认拒绝 | 没有显式授权，就默认不能做。 |
| 最小权限 | 只给完成当前任务所需的最小能力。 |
| 白名单优先 | 工具、目录、命令、网络目标都优先白名单。 |
| 按风险分级 | 不同动作走不同审批与护栏，不搞一把梭。 |
| 关键动作确认 | 删除、联网、执行、外发，必须再停一下。 |
| 副作用隔离 | 能在沙箱做的，绝不直接碰真实环境。 |
| 全链路可观测 | 每一步看得见，异常能立刻发现与告警。 |
| 结果可回滚 | 不怕出错，怕的是改了以后撤不回来。 |

#### 动作分级矩阵

| 动作 | 策略 |
| --- | --- |
| 读取文件 / 搜索代码 / 看日志 | 自动执行 + 留痕 |
| 修改代码 / 写配置 / 生成补丁 | 受策略限制放行 |

## 上下文处理相关

### 从源码泄露事件看 Claude Code 是怎么“装上下文”的

这张图不是讲泄露本身，而是把泄露后能观察到的结构，整理成一张适合课堂讲解的上下文管理架构图：输入从哪里来、怎么筛、怎么压缩、怎么回灌，以及为什么长任务能续航、也为什么会失真。

- 分层拼装：系统、项目、任务、历史、工具结果分开处理。
- 循环回灌：一次模型输出，往往会成为下一轮输入的一部分。
- 压缩续航：长上下文靠摘要与裁剪维持，而不是全量硬塞。

Claude Code 的关键不是“看到全部”，而是“每一轮都挑对该看的内容”。

#### 上下文中枢

筛选 · 拼装 · 压缩 · 回灌

右侧卡片部分被浮层挡住，可见文字如下：

- 系统提示词：角色、边界、工具规则，是最？些材料。
- 任务焦点：当前问题决定这一轮到底该带哪？
- 项目规则：？DE.md / 仓库约定，把这个项目怎么做带进来。
- 工具结果：读文件、搜代码、执行命令？果会回流进下一轮。
- 安全边界：并非所有内容都能进入模型，仍受边界与权限约束。
- 记忆与摘要：任务需记忆和摘要维持？不是全量重放。

### 一、上下文从哪里来

“输入源”。Claude Code 不是把所有东西一次性扔进模型，而是把不同来源拆开处理，再按任务需要重新组合。

| 来源 | 说明 | 标签 |
| --- | --- | --- |
| 系统提示词碎片 | 角色定位、工具约束、安全边界、行为偏好等基础规则。 | 稳定、高优先级 |
| 项目规则 / CLAUDE.md | 把仓库习惯、编码风格、目录结构与任务规则注入上下文。 | 项目级、可配置 |
| 当前对话与任务 | 用户当前要求、明确目标、临时约束，是本轮最直接的驱动力。 | 近期、强相关 |
| 文件读取结果 | 读到的代码片段、配置、输出结果，决定接下来该看什么、改什么。 | 工具观察、证据输入 |
| 会话历史 / 摘要 | 长对话会被折叠成摘要，保留关键结论而不是原文堆积。 | 压缩、续航 |
| 权限 / 安全边界 | 不是所有信息都能原样进入上下文，仍要经过边界控制与过滤。 | 限制、防污染 |

### 二、它是怎么把上下文拼成请求的

“关联与装箱”。核心是：先判断相关性，再按 token 预算装配，最后送入模型。

| 序号 | 步骤 | 说明 |
| --- | --- | --- |
| 1 | 候选上下文池 | 把系统、项目、历史、任务、工具结果放进候选池。 |
| 2 | 相关性筛选 | 挑出与当前任务最有关的片段，弱相关内容先放后面。 |
| 3 | Token 预算分配 | 决定哪些内容完整保留，哪些内容摘要化，哪些直接裁掉。 |
| 4 | 静态 / 动态分离 | 稳定规则做底座，变化内容临时注入，更利于缓存与复用。 |
| 5 | 最终请求包 | 被挑选和重组后的上下文，作为这一轮模型真正能看到的输入。 |
| 6 | 模型推理 | 模型基于“可见上下文”做判断：回答、规划或继续调用工具。 |

### 三、长任务为什么能续航

“压缩与回灌”。最关键的是，旧信息不会无限原样保留，而是通过摘要和再装箱延续任务连续性。

| 机制 | 说明 |
| --- | --- |
| 历史压缩 | 较早的对话与过程被折叠成摘要，保留核心结论。 |
| 近期优先 | 越接近当前动作的内容，越容易保留完整原貌。 |
| 工具结果回灌 | 读取、搜索、执行命令后的结果会进入上一轮上下文。 |
| 再压缩再进入 | 上下文持续膨胀时，再次压缩，形成循环运行机制。 |

### 四、这套机制的风险点

“为什么会失真”。摘要越强，越可能丢细节；工具回灌越多，越要防污染。

| 风险 | 说明 |
| --- | --- |
| 摘要失真 | 压缩后保留的是“结论”，不一定保留完整语境，细节容易丢。 |
| 上下文投毒 | 一旦错误信息混入工具结果或历史摘要，后续轮次会被持续放大。 |
| 错误固化 | 摘要会把旧错误“写成看起来更稳定的事实”，越跑越难纠正。 |
| 边界误入 | 不该进入上下文的内容如果进入了，会影响判断和后续执行安全。 |

### 五、收尾的四个结论

最后的总结页。

| 结论 | 说明 |
| --- | --- |
| 不是“全塞进去” | Claude Code 的核心是选择性装配，而不是暴力堆上下文。 |
| 不是“一次完成” | 它更像连续循环：模型、工具、回灌、压缩，不断重复。 |
| 压缩能续航，也会失真 | 长任务靠压缩跑得更久，但摘要会带来信息折损。 |
| 工具链既是入口，也是风险点 | 工具把真实世界带入上下文，也可能把噪声带进去。 |

## 上下文管理结构

### 从 Claude Code 源码泄露引出它的上下文管理架构

基于 Claude Code 源码泄露事件，对上下文管理思路进行反推。

这次分享不展开事件细节，重点是借助泄露出来的实现线索，去理解 Claude Code 为什么能在长任务中持续保持有效上下文。

核心主线：多源输入 → 上下文编排 → 压缩摘要 → 持续回写

上下文编排核心：不是堆聊天记录，而是动态拼装。

周围输入：系统规则、工具定义、仓库信号、会话历史、项目记忆、压缩摘要。

| 问题 | 说明 |
| --- | --- |
| ① 上下文从哪里来 | 系统、工具、仓库、历史、记忆共同参与 |
| ② 上下文怎么被筛选 | 进入模型前先做预算、裁剪、摘要 |
| ③ 上下文怎么持续工作 | 工具反馈会回写，形成记忆闭环 |

### ① 上下文从哪里来

Claude Code 在真正向模型发请求前，究竟把哪些信息当成“可用上下文”。

| 来源 | 说明 | 标签 |
| --- | --- | --- |
| 系统规则 | 定义角色、安全约束、回答风格、执行边界，是整套上下文的“硬地板”。 | 安全、身份、输出约束 |
| 工具定义 | 告诉模型它能读什么、改什么、查什么、执行什么。工具 schema 本身就是上下文的一部分。 | Read、Edit、Shell |
| 仓库信号 | 文件树、关键文件、git diff、报错位置、测试结果，这些决定“当前代码世界长什么样”。 | 文件树、diff、测试 |
| 当前任务 | 用户目标、子任务拆解、失败点、最近一次尝试，决定模型这一轮最该关注什么。 | 目标、子任务、失败点 |
| 会话历史 | 近几轮对话、前序工具结果、之前的选择理由，构成当前的“工作记忆”。 | 最近轮次、工具回执、决策轨迹 |
| 项目级记忆 | 把高复用、跨轮次稳定的信息存起来，避免每一轮都重新“认识项目”。 | 规则、记忆、摘要 |

### ② 真正关键的不是“收集”，而是“怎么拼”

编排层 / Orchestration

Claude Code 之所以不像普通聊天工具那样越聊越乱，是因为它在进入模型前就做了预算、筛选和压缩。

| 步骤 | 名称 | 说明 |
| --- | --- | --- |
| 01 | 收集候选上下文 | 从系统规则、工具、仓库、历史、长期记忆中，把所有可能有用的信息拉进候选池。 |
| 02 | 归一化与去噪 | 把重复、冗长、低价值的信息整理掉，避免同一事实反复占窗口。 |
| 03 | Token 预算分配 | 先决定谁必须留下、谁可以摘要、谁暂时不带，这是上下文管理的转折点。 |
| 04 | 组装 Prompt | 把规则、任务、历史、工具 schema、仓库信号拼成结构化提示，而不是简单拼接文本。 |
| 05 | 监测窗口饱和 | 一旦上下文逼近上限，就准备进入 compact / summary，避免后续失真。 |
| 06 | 压缩高价值事实 | 把冗长轨迹压成短摘要，只保留目标、关键决定、当前状态、未完成项和风险点。 |
| 07 | 发给模型继续工作 | 最终送入模型的不是全部历史，而是对当前轮次最有用的可执行上下文。 |

### ③ 三层记忆：为什么它不只是一个聊天窗口

记忆层 / Me？

短期工作集、项目记忆、压缩快照共同承担“记忆”职责，这也是上下文关联最容易讲透的一块。

#### 第一层：会话工作集

离当前任务最近、最热、变化最快。通常包含最新轮次、刚读过的文件、刚执行过的工具结果，以及模型当前行动计划。

- 最近对话与任务目标
- 当前相关文件 / 代码片段
- 最新测试与报错结果
- 当前轮的行动计划

讲解抓手：最重要，但也最容易膨胀。如果这里不做预算，token 消耗会非常快。

#### 第二层：项目级记忆

把高复用、跨轮次稳定的信息存起来，避免每一轮都重新“认识项目”。

- 仓库规则 / 编码规范
- 模块关系 / 架构常识
- 常见命令 / 工作流偏好
- 项目摘要与长期约束

#### 第三层：压缩摘要快照

当历史变长时，把冗长过程压缩成可复用结论，在下一轮继续作为高密度上下文。

- 当前目标与完成进度
- 已做决定 / 已验证结论
- 未解决问题 / 风险点
- 下一轮应继续什么

### ④ 完整闭环：每一次工具执行，都会反过来改写下一次上下文

反馈闭环 / Feedback Loop

它不是答完就结束，而是在工具调用后不断把环境反馈重新注入上下文。

| 步骤 | 说明 |
| --- | --- |
| 模型先给计划 | 先决定读文件、查 diff、跑测试还是直接改代码，形成当前轮的行动路径。 |
| 调用工具执行 | 通过 read / edit / shell 等工具与真实仓库交互，不是只在脑内推理。 |
| 接收环境回执 | 文件内容、报错、测试结果、命令输出进入新的观察层，成为事实输入。 |
| 更新工作记忆 | 把最新发现替换旧判断，减少模型继续沿着过时认知走下去的风险。 |
| 必要时做 compact | 当轨迹过长，就把过程压成结论，为下一轮腾出窗口。 |
| 重新组装再发起 | 新一轮请求不是复读旧上下文，而是基于最新状态重新拼装最优上下文。 |

### ⑤ 讲这张图时，最容易让听众听懂的两个抓手

讲解抓手 / Ta？

不必展开源码细枝末节，围绕“为什么这样设计”来讲，听众会更容易抓住重点。

#### 为什么上下文管理会成为 AI Coding Agent 的核心壁垒

| 序号 | 要点 | 说明 |
| --- | --- | --- |
| 1 | 不是谁都能拿到正确上下文 | 真正难的是把代码世界、工具世界和对话世界拼成一个可执行 prompt。 |
| 2 | 不是越多越好，而是越准越好 | 窗口有限，错误信息进得越多，模型越容易偏航、烧 token、重复劳动。 |
| 3 | 压缩能力决定可持续性 | 如果不能把长轨迹压成高密度记忆，长任务几轮之后就会开始失真。 |

#### 你可以用这 3 个问题带着听众看完整张图

| 问题 | 对应内容 |
| --- | --- |
| 哪些信息必须保留？ | 系统规则、当前任务、关键文件、最新工具回执、稳定项目规则。 |
| 哪些信息应该被压缩？ | 过长对话轨迹、重复工具输出、已经确认过的中间过程。 |
| 什么时候回写到长期记忆？ | 当某些信息跨轮次稳定有效，并且值得下次直接复用时。 |

底部标签：

- 泄露事件：反推出实现思路的起点
- 工作记忆：离当前任务最近
- 项目记忆：跨轮次稳定复用
- 压缩摘要：把过程变成结论
- Token 预算：决定谁进上下文
- 工具回执：不断刷新事实世界

### 泄露后最值得讲的核心结论

Claude Code 的上下文关联，本质上不是“把历史越塞越多”，而是把真正有价值的信息挑出来、压缩好、持续回写，再在下一轮重新装配。

| 结论 | 说明 |
| --- | --- |
| 上下文是多源输入 | 系统提示、工具能力、仓库状态、任务目标、历史轮次、长期记忆一起参与，不是只靠聊天记录。 |
| 中间有预算与筛选 | 上下文窗口有限，所以必须先排序、截断、裁剪、抽取重点，再进入最终 prompt。 |
| 接近上限就压缩 | 不是等窗口爆掉才处理，而是通过 compact / summary 把冗长轨迹压成高密度记忆。 |
| 压缩后会回写复用 | 短期工作集、项目记忆、摘要快照相互配合，形成可持续的编码记忆闭环。 |

## RAG系统

### 全链路定位：RAG 系统中的精排枢纽

1. 粗排召回 (Retrieval) → 2. 核心精排 (Rerank) → 3. 知识生成 (Generation)

#### 1. 粗排召回 (Retrieval)

- 工具库：向量数据库 / 倒排索引
- 策略：双路召回 (Semantic + BM25)
- 输出：海量数据中捞取 Top 100 候选集

#### 2. 核心精排 (Rerank)

- 主角：LambdaMART
- 动作：融合多维特征，重新打分
- 输出：锁定最核心的 Top 5 黄金文档

#### 3. 知识生成 (Generation)

- 主角：大语言模型
- 输入：Prompt + Top 5 黄金文档
- 输出：拒绝幻觉的精准专业回答

### LambdaMART 内部透视

#### 它是如何工作的? (GBDT + LTR)

它是 Learning to Rank (LTR) 领域的霸主，属于 Listwise 列表级排序算法。

- 躯干 (MART)：梯度提升决策树，极速拟合特征。
- 灵魂 (Lambda)：解决排序指标（如 NDCG）不可导的难题，通过交换文档位置算出的“动态梯度”。

#### 多源特征融合矩阵 (工业界杀手锏)

| 特征 | 内容 |
| --- | --- |
| 文本 | BM25 / TF-IDF 分数 |
| 语义 | 交叉编码器输出分数 |
| 业务 | 文档时效性 / 更新频率 |
| 反馈 | 历史点击率 / 点赞数 |
| 元数据 | 文档长度 / 权威度 |

### 方案对决：为什么不只用神经网络？

| 排序方案 | 核心原理 | 推理速度 | 工业界适用场景 |
| --- | --- | --- | --- |
| 传统算法 (BM25) | 词频与逆文档频率统计 | 极快（毫秒级） | 仅作为基线或初步粗排，无法理解语义 |
| 交叉网络 (Cross-Encoder) | 深层网络直接拼接 Query 与 Doc | 缓慢（计算昂贵） | 对算力极度充裕且只排极少量文档（如 Top10）的场景 |
| LambdaMART + 混合特征 | 树模型集成：统计特征 + 神经网络特征 | 极速（森林推理） | 当前高并发 RAG 系统的标配，兼顾性能与效果，完美融合业务规则 |

### 面试通关一锤定音总结

#### 1. 站位精准

它处于粗排之后、大模型生成之前的精排 (Rerank) 环节。旨在解决大模型上下文窗口限制及“中间迷失”问题，将最精准的知识喂给模型。

#### 2. 核心原理

本质是 MART（树模型）+ Lambda（排序梯度）。通过优化 NDCG 等 Listwise 列表级指标，而不是单纯的点对点分类，实现全局排序最优。

#### 3. 工业界不可替代性

大模型和交叉网络推理慢且只能处理文本。LambdaMART 可以作为最强集成器，在毫秒级时间内融合文本匹配度、神经网络语义得分以及业务元数据（点击率/时间）。

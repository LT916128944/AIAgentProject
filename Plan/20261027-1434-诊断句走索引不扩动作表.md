## 1. Summary

动作表继续只做执行器合同。组合仍由理解器做。一句只读的「看看有没有问题」在表里没有对应行时，用源码里已声明的 Automation 过滤器和台账做唯一性归地，归得上就收成现有的 `run_automation_test`。归不上就维持能力缺口。不新增玩法动作，不把这句收成 `implement_shooter` 或 `check_platform_hud`。

落点是 `RAG/ue-rag` 的范围补窗。仿 `agent/supervise.py` 的 `unique_automation_filter`：零条或多条都返回空，不挑。

## 3. 已确认决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 动作表还要不要 | 留着，只表示执行器合同 | 副作用和裁判种类有限；用户句子的组合是无穷的，不往表里加行 |
| 谁做组合 | 理解器，沿用现在的表内动作加原句 token | 已经是模型在做，不必再写短语表 |
| 冷门诊断句 | 代码用索引归地到已有只读动作。归地失败才是能力缺口 | 模型补邻近动作会把「检查射击」收成没有名字的 `query_actor` 或平台 HUD |
| 本轮归地收成什么 | 唯一过滤器 → 一扇 `run_automation_test` | 这是表里现成的只读动作，带 `automation` 裁判。不新写场景统计动作 |
| 不收成什么 | 不收成 `implement_shooter`，不收成 `check_platform_hud` | 前者会改关卡；后者核对的是平台跳跃 HUD 控件名 |
| 怎么算唯一 | 诊断句先对上台账里恰好一个范围；用该范围标题和备注里的 ASCII token 做 `unique_automation_filter` 的 needle。恰好一条才采用 | 「射击」对不上 `AIAgent.Fps.Hit`。台账标题里的 `FPS` 可以。不写「射击 → Fps」字典 |
| 原句里已有的过滤器 | 原句 token 能唯一命中时直接用，不再查台账 | 人点了名就以人的为准 |
| 零条或多条 | 零条：`scope_windows` 返回 `[]`，范围维持缺口。多条：一扇暂停窗，错误写明候选过滤器，问一次过滤器全名 | 不挑，不问 `/Game` |
| 关卡名 | 原句或同一次规划里已经点名的关卡，诊断窗不改写、不另开一扇 `open_level` | 这次原句点的是 `level3`，台账里的射击在 `L_NewTest3`。过滤器自己会建临时世界 |
| 什么句子走这条 | 只读诊断：含「看看」「检查」「核对」「是否有问题」「有没有问题」，且不含「实现」「新建」「创建」「修改」「摆」「放置」 | 「在 L_NewTest3 内实现简易 FPS」必须仍然是 0 扇，现有评测依赖这一点 |
| 确认过的缺口 | 仍不把 `complete` 传进补窗 | 归地是代码，预演已经算过。确认之后再叫模型，就是 142031 那次 |
| 候选表 | 本轮归地失败不调用 `note_candidate` | 失败原因是没有唯一过滤器，不是缺一个新动作名 |
| 不改谁 | `catalog.py` 的键、`lexicon.json`、`understand.py` 的提示词、`implement_shooter` 的执行、游戏源码 | 玩法脚本不再增长；本轮也不趁机删旧脚本 |

## 4. Proposed Changes

下一轮按这个顺序改。

1. **新建 `agent/diagnose.py`** — 纯函数，不叫模型，不写盘，不连编辑器。
   - `is_diagnostic(text) -> bool`：按第 3 节的只读词和排除词判断。
   - `ground_diagnostic(text, ledger_path=None) -> dict`：返回 `{"ok": True, "filter": "<已声明全名>"}`，或 `{"ok": False, "filters": [...]}`（多条，可为空）。
   - 先用原句里的 ASCII token 调 `unique_automation_filter`。有唯一结果就返回。
   - 否则读台账。范围标题去掉 `ledger._GENERIC` 之后，与诊断句的重合恰好落在一个范围上，才把该范围标题和备注里的 ASCII token 交给 `unique_automation_filter`。零个范围或多个范围都是失败。
   - `ledger_path` 默认 `ledger.LEDGER_PATH`。评测传入临时文件。
2. **`agent/plan_windows.py` `scope_windows`** — 在 `_try_blueprint_create` 之后、`if callable(complete)` 之前调用诊断归地。
   - 范围文字不是诊断句：行为与现在相同。
   - `ok` 且过滤器非空：`materialize_goal("run_automation_test", {"filter": ...})`，再 `_scope_reid`。窗口 `realizable` 为真。
   - `filters` 长度大于 1：一扇暂停窗，`action` 为 `run_automation_test`，`error` 为「过滤器不是唯一的一条：A、B。只给一次：r 过滤器全名。」不写入任何一条过滤器。
   - `filters` 为空：返回 `[]`。
   - 诊断句即使传了 `complete`，也不再调用 `windows_for_clause`。
3. **`agent/run_windows.py`** — 仅当暂停错误含「只给一次：r 过滤器全名」时：
   - 提示改为「裁决：s 停止 / c 跳过 / r 过滤器全名」。
   - `_apply_path` 把回复交给 `declared_automation_filters()`。回复与其中一条全名一致，才写回 `slots.filter` 和 `automation_filter`，窗口改为可执行。其余回复维持现在的「补路径无效，这一窗仍暂停」。
   - `release_unfilled_slots` 继续跳过「缺少槽位 name」这类写不回路径的暂停。不要把「过滤器不唯一」算进这一类。
4. **新建 `eval/check_diagnose.py`** — 不连编辑器，不叫模型。`UE_SOURCE_ROOT` 指到临时目录，里面放一份含 `IMPLEMENT_SIMPLE_AUTOMATION_TEST` 的 `.cpp`。台账用临时 json。覆盖第 6 节的四条。

## 5. Assumptions

- 诊断归地只产生 `run_automation_test`。场景里有没有 `FpsPawn` 不在本轮做；那需要新的只读执行器，本轮不加。
- 台账范围和诊断句对不上时，结果是缺口，不是再去检索资产库挑一个类名。`search_ue_project` 的标题不参与归地。
- 若下一轮发现「实现 FPS」被 `is_diagnostic` 认成诊断句，停在这一条，收紧排除词。不要为了让「看看射击」跑起来而改掉 `eval/check_implement_shooter.py` 里「实现简易 FPS 必须是 0 扇」的断言。
- 人在多条过滤器里回复的字符串必须与源码声明全名一致。大小写不同、只写最后一段，都视为无效，不猜测。

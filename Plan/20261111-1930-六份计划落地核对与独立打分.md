### 3.2 说过头的一处：分数到底由什么撑起来

`README.md:64` 与 `WORKFLOW.md:60` 都说「分数以 `check_scorecard.py` 打印的为准，没有人签、基准档案没跑满时，对应维度停在现状分」。这句话本身没错，但**没说清「现状分」是怎么来的**：

- 没有档案时 B 停在 **16**，这 16 分**不是任何证据算出来的，是脚本里写死的 `BASE["B"] = 16`**（`eval/check_scorecard.py:19`）。读起来像「已经拿到了 16 分，只差 3 分」，实际是「16 分没有证据，脚本选择不扣」。
- C/D/E/G/H 五维读的是本机 `check_all.json` 的**缓存退出码**，不是当场重跑。文件旧了、或被别的进程写过，这五维就跟着走。
- 文档没提「B 需要 10 句 × 3 轮真机」，只在 `eval/bench_manifest.json` 里。

**建议改文档侧**：`README.md:64` 与 `WORKFLOW.md:60` 各加一句——「B 的 16 分是起点分，不是已验分；本轮没有任何完成记录时，16 分只表示『档案缺失』，不表示『通过了 16 分的检查』」。

### 3.3 一处真漂移：`.env.example` 的求解开关

`README.md:37` 写「复制 `.env.example` 得到的是这台机器正在用的值……求解开关 `UE_SOLVER_ENABLED=true`」，`README.md:81` 写「本机 `.env.example` 为 true」。实际 `RAG/ue-rag/.env.example` 里这一行是**注释**：

```text
# UE_SOLVER_ENABLED=false
```

复制出来不会得到 `true`，得到的是「不设」，代码缺省是关。

`eval/check_risk.py:219-236` 之所以没红：它只在 README 出现「本机已开」这四个字时才去查 `.env`，而现在 README 用的是「本机 `.env.example` 为 true」这种更容易误读的写法，绕过了断言。**这是断言口径与文档措辞一起漂了的地方。**

## 4. 我的评估方式与分数

### 4.1 评分口径

沿用 1425 第 3 节的九维与满分（8/19/15/12/12/10/9/7/6 = 100），**不改维度、不改权重**。改的只有一件事：

> **每一分都要说得清「这一分由哪份证据撑着」，且这份证据是用户自己跑出来的。**

据此把每分的证据分成三档，再按档打折：

| 档 | 定义 | 计分 |
| --- | --- | --- |
| **真证据** | 由真实运行产生、模型和脚本都伪造不了：用户原句端到端记录、人签、真机自动化结果 | 全额 |

## 5. 打分方法本身的缺陷（这是抬到 95 的前提）

按严重度排：

1. **B 没有生产者。** 十句基准的 `verdict.json` 没有任何代码写 `ok`/`partial`/`failed`。`run_bench.py` 只写 `skipped`；6 份 `ok`/`failed` 是手改的。`data/archive/` 又被 gitignore。**结果是：16 分和未来 3 分的加分，都可以靠手改一个不被版本控制的 JSON 拿到。** 这是最大的洞，也是「92 分」不可信的主要原因。
2. **基线分被当成已得分。** `BASE = {A:7, B:16, ...}` 是起点，`check_scorecard` 只在拿到证据时往上加，拿不到时不扣。它的输出叫「总分 92」，读者会以为 92 是验出来的。**要么把基线标注成「未验」，要么把基线降到 0 再逐条加。**
3. **谓词吃缓存。** C/D/E/G/H 读本机 `check_all.json` 的退出码。文件可以旧、可以被别的进程写。`check_all.py` 自己会重跑一遍（45 条），但 `check_scorecard` 在没设 `UE_CHECK_ALL_SUMMARY` 时会**自己拉子进程重跑**——两条路径的强度不一样，文档只写了后者。
4. **两个谓词不在 CI。** `check_distill.py`（G）不在 `offline.yml`，CI 上 G 永远不会被重跑，只剩本机缓存。同理 `check_score_gate` 之外的 `check_scene_gate.py`、`check_diagnose.py`、`check_implement_shooter.py`、`check_empty_deliverable.py`、`check_deliverable_coverage.py`、`check_blueprint_stop.py`、`check_open_inspect.py`、`check_solver_plan_parse.py` 也不在（57 个 `check_*.py`，44 个进了 CI）。
5. **恒真形状谓词。** I 的两个分支：顶层 `ok: True` 写死；五字段只验形状。F 的 `_caller_split` 喂内联 dict。E 的 `compensating` 只验字符串出现。
6. **没有一条谓词要求「用户原句端到端跑通」。** 九维里覆盖「整句」的只有 B，而 B 没生产者。`open-level` 三连败就是活例子：**离线 `plan_windows` 给的是 `rules` 两扇，在线却进了 `solver-fallback` 一扇 solve 然后失败。** 离线绿不等于在线能跑，而记分只看离线。
7. **文档漂移不在记分里。** 只有 `check_risk` 的求解开关那一条读文档。`README.md:37/81` 与 `.env.example` 的漂移、`README.md:116` 的 `--profile`、`UE_ALLOW_PYTHON` 不在任何开关表，都不影响分数。
8. **计划自己前后不一致。** 1425 第 48 行说三份做完到 92，第 65–66 行说到 88，差值是 1429 的 F+1/I+2。对外报分时容易把 1429 的功劳记到前三份头上。
9. **合规留白。** 六份计划都写 `pre_authorized: false`，代码已落地、文档已改写，`RAG/ue-rag` 有 50 处未提交改动。这批改动缺一次显式确认记录。
10. **离线绿 ≠ 在线能跑。** `open-level` 三连败（2.5 节）不是「检查漏了」，是**离线检查与在线路径根本不是同一条**：离线封闭环境下 `plan_windows` 走 `source=rules` 两扇，在线却 `solver-fallback` 一扇 solve。现在没有任何一条检查比对这两条路径。这是把分数抬到 95 时最该修的结构性缺口。

## 1. 结论

`start.bat` 的菜单 2 让出现在的菜单 3 盖掉。`run_agent.py` 不再作为日常入口。现在的菜单 3 是一张图上的多角色，不是多 Agent。

真正的菜单 3 是多扇窗口。规划者单独开一轮，只看用户那句话和一张动作表，拆成窗口清单。每一扇窗口自己跑一遍现有的 LangGraph（`retrieve → plan → execute → build → test → observe → fix`），用自己的 `thread_id` 和自己的消息。窗口之间不传递工具原文。最后一扇只做集成裁决。

规划者拆出的步骤只要代码判定可实现，就写回 `plan_sequence` 的快路径。下一句同一句式不再叫规划者。

编辑器是单进程。窗口按依赖顺序跑，同一时刻只有一扇能编译或写场景。

## 3. 参照

图里的表是窗口清单，不是又一个对话产品。每一行是一扇窗口：任务范围、这扇要做完的内容、本窗口的预算。表下有依赖，最后一行是集成、验证与交付。各行可以同时存在，但有依赖的行必须等上游。

公开架构里和这件事对齐的是：

| 来源 | 取什么 |
| --- | --- |
| Anthropic《Building Effective Agents》编排器-工人 | 编排器按这句话拆子任务，工人执行，编排器只看结果 |
| Claude Code 子代理 | 子代理是干净上下文，只把摘要交还。中间的工具原文不回父会话 |
| LangChain 2026：不再维护 `langgraph-supervisor` 这个包 | 工人包成一次调用。不把工人的消息历史交回规划者。不为此引入那个包 |

不照搬的：多虚拟机并行改同一份工程、工人之间直接传完整对话、把 830 个工具 schema 交给规划者。UE 编辑器和 `cpp_build` 会关编辑器、占 DLL，不能两扇窗口同时写。

## 5. 菜单 3 怎么走

```text
用户一句话
  │
  ▼
快路径 plan_sequence
  手写规则或已学路径能拆开 → 直接跑，不叫规划者
  得到「写不成任务」       → 才开规划者
  │
  ▼
规划者（新的一轮模型调用）
  系统提示：只有动作表。没有检索、没有工具 schema、没有上一扇的工具原文
  用户消息：只有这句自然语言
  输出：窗口清单 JSON
  │
  ▼
代码验收清单
  action 必须在表里
  槽位里的类名、BP_、/Game/ 由代码解析
  解析失败的窗口暂停，不猜，后面依赖它的窗口不跑
  整句窗口都可实现 → 写回快路径（见 5.5）
  │
  ▼
调度
  按 depends_on 排序
  写编辑器或 cpp_build 的窗口串行，一把锁
  │
  ▼
窗口 W1、W2、…  每扇 = 现有 run_task
  新的 thread_id
  新的 messages，内容只有这扇的任务句
  成功或失败只交回 {id, ok, summary, judge}
  │
  ▼
集成
  无模型。全部依赖满足且裁判 ok，整句才 ok
  某一扇失败只重试这一扇，次数用它自己的 max_retries
  不把别的窗口再跑一遍
```

规划者输出长这样。字段就这些，不要散文：

```json
{
  "windows": [
    {
      "id": "W1",
      "title": "把 BP_TestActor 设为可拾取",
      "action": "set_pickable",
      "slots": {"target": "BP_TestActor"},
      "depends_on": [],
      "max_retries": 1
    },
    {
      "id": "W2",
      "title": "只读裁决能否被 BP_TestPawn 拾取",
      "action": "judge_pickup",
      "slots": {"target": "BP_TestActor", "picker": "BP_TestPawn"},
      "depends_on": ["W1"],
      "max_retries": 0
    }
  ]
}
```

和参照表的对应：`title` 是这扇要做完的内容，`action` 加 `slots` 是任务范围，`depends_on` 是表下的依赖，`max_retries` 是本窗口预算。不估算小时。

### 5.1 动作表

第一版只放执行器已经会做的，外加一格「设为可拾取」。规划者不能写出表外的 `action`。

| action | 槽位 | 窗口里跑什么 | 写场景 |
| --- | --- | --- | --- |
| `compile_project` | 无 | 现有编译工程。`freeze_source`。句里要启动编辑器时带上 | 关编辑器再编译 |
| `compile_blueprint` | `blueprint` | 现有 `blueprint_compile` | 否 |
| `edit_cpp` | `class` | 现有改唯一 C++ 类。类不是一个就暂停 | 改源码 |
| `bind_blueprint` | `class` 或 `blueprint` | 现有槽位解析。没有资产且人给了路径才新建，父类去掉 `A`/`U`/`F` | 可能新建资产 |
| `place_actor` | `blueprint` | 现有放入关卡。不保存 | 是 |
| `judge_pickup` | `target`、`picker` | 现有只读裁决。不写标签 | 否 |
| `set_pickable` | `target` | 见 5.2 | 是 |
| `move_actor` | `actor`、坐标 | 现有移动 | 是 |

`set_pickable` 是「给 BP_TestActor 打上可交互标签」能落地的那一格。没有这一格，规划者仍然只能拒。

### 5.2 `set_pickable`

`ATestActor` 构造时 `bPickable` 为 false，`bAllowPickup` 为 true。`ApplyPickable` 只在 `bPickable` 为真时加上 `InteractableActor`。只写 `Tags` 会和这个函数分叉。

这一扇要达成 `SetPickable(true)` 的结果：`bPickable` 为真，且带 `InteractableActor`。下一轮先 `scan_mcp_tools.py` 找调用 `BlueprintCallable` 的工具。找到就调 `SetPickable`。找不到就对实例同时写 `bPickable` 和 `Tags`，不写别的字段。写完用现有只读裁决再查，不把「写过了」当成成功。

不 PIE。不保存关卡。

### 5.3 那句原话会变成两扇窗口

「给场景的 BP_TestActor 的 tag 标记为可交互物，使得 BP_TestPawn 可以与它交互」

| 窗口 | action | 依赖 | 做完的标准 |
| --- | --- | --- | --- |
| W1 | `set_pickable`，target=`BP_TestActor` | 无 | 实例 `bPickable` 为真且带标签。场景里没有这个实例则失败，不假装写成了 |
| W2 | `judge_pickup`，picker=`BP_TestPawn` | W1 | 四条都满足才是「能」。距离不够仍是「不能」，不算 W1 失败 |

W2 的「不能」是裁决结果，整句仍然跑完。W1 没写成，整句失败，不跑 W2。

### 5.4 上下文边界

| 谁 | 看得到 | 看不到 |
| --- | --- | --- |
| 规划者 | 这一句原文，动作表 | 检索块、MCP schema、技能正文、任何窗口的工具返回 |
| 一扇窗口 | 自己的任务句、自己的角色工具、自己的裁判错误 | 别的窗口的 `messages` |
| 集成 | 每扇的 `{id, ok, summary}` | 工具原文 |

代码在两扇之间传递的是已经解析好的 `ref_path` 和实例是否在关卡里，放在下一扇的任务 JSON 里，不放进规划者的下一轮对话。

### 5.5 可实现的步骤写回快路径

规划者只负责第一次。代码收下整句窗口之后，把句式写进快路径，下一次 `plan_sequence` 在开口叫模型之前就能拆开。

可实现指：每个 `action` 都在动作表里，每个槽位都解析成了唯一的类、蓝图或 Actor。场景里暂时没有实例、编译失败、裁决是「不能」，都不妨碍写回。分解已经能跑，世界状态是另一回事。

有任一窗口不可实现（表外 action、槽位零条或多条、人还没补的路径）就不写。不把半句猜进快路径。

落盘不改 `supervise.py` 的手写正则。新建 `agent/learned_routes.json`，`plan_sequence` 在现有规则之后、规划者之前读它。模型不改 Python。

一条路径只记句式和槽位角色，不把这次的 `BP_TestActor` 写死：

```json
{
  "id": "mark-interactable",
  "when": ["标签", "可交互"],
  "roles": ["target", "picker"],
  "windows": [
    {"action": "set_pickable", "slots": {"target": "target"}},
    {"action": "judge_pickup", "slots": {"target": "target", "picker": "picker"}, "depends_on": ["W1"]}
  ]
}
```

`when` 来自这句里点名的动作词（标签、可交互、tag、交互），由代码从原句抽取，不让模型另写一套正则。下一句要同时含这些词，并且能抽出同样数量的蓝图或类名，才命中。抽不出仍去找规划者。

同一 `id` 已在文件里就不重复追加。运行失败不删这条。人要作废就删文件里的那一条。

写回发生在验收通过之后、窗口开始执行之前。这样第一次叫了规划者，第二次起走快路径，不必等 UE 跑完才记住句式。

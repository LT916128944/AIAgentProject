# 平台跳跃关卡需求差距分析与下一目标

## 需求原文

在 UE 5.8 里做一个能玩的平台跳跃关卡：旋转发光的金币、左上角计数和 90 秒倒计时、收齐开门显示通关、后段平台会动…

## 结论

**当前系统不能完整满足这一需求。** 按现有能力走一遍流程，会得到与巡逻敌人同构的「部分完成」：C++ 逻辑半边可以闭环（金币旋转与重叠计数、收齐开门条件、移动平台、90 秒倒计时组件，`edit_cpp` + `cpp_build` 裁判），表现与验证半边过不去（发光材质、UMG HUD、通关显示、玩法级「能玩」验收）。因此本次不启动闭环跑流程——每个新类都要过 `ue-cpp-plan` 人审确认门，而表现半边注定停在 `manual`/`pending`，跑了也拿不到「能玩」的测试结果。缺口已钉进 `RAG/ue-rag/data/harness/feature_list.json` 四条新 pending（`material-domain` / `umg-domain` / `platform-automation` / `level-assembly`），下一目标从第一条 pending 做起。

核对基准（2026-10-20）：九条离线检查全绿；`UE_ALLOW_BLUEPRINT=true`（本机 `.env`），`UE_ALLOW_MATERIAL / UMG / ANIM / NIAGARA` 均为 `false`；动作表十个动作全部在 C++ 与 Actor 放置域。

## 逐项能力映射

| 需求子项 | 需要什么 | 系统现状 | 判定 |
| --- | --- | --- | --- |
| 平台布局（关卡本体） | 批量放置平台 Actor | `place_actor` / `move_actor` 可放（内存态，不保存关卡；`save` 默认拒） | ⚠️ 逐个可行；批量布置与保存缺流程 |
| 旋转金币 | 新类 `ACoin` + `URotatingMovementComponent` + 重叠计数 | `edit_cpp`（唯一类门 + `ue-cpp-plan` 确认门）+ `cpp_build` 裁判；旋转用引擎组件，不需要改图 | ✅ 可做（C++ 半边） |
| 发光 | 材质 Emissive 或 MID 参数覆写 | `UE_ALLOW_MATERIAL=false`；动作表无材质动作；材质域没有 `ue-manual-blueprint-skill` 的对应人工步骤产出 | ❌ 缺口 |
| 左上角计数 HUD | UMG Widget Blueprint + 绑定 | `UE_ALLOW_UMG=false`；动作表无 UMG 动作 | ❌ 缺口 |
| 90 秒倒计时 | C++ 计时逻辑 + HUD 显示 | C++ ✅；显示走 UMG ❌ | 半 |
| 收齐开门 | C++ 计数条件 + 门 Actor 移动 | `edit_cpp` 写逻辑，门移动可纯 C++ | ✅ 可做 |
| 显示通关 | UMG 通关画面 | 同 UMG ❌ | ❌ 缺口 |
| 后段平台会动 | 新类 `AMovingPlatform` | `edit_cpp` ✅（Tick 或插值） | ✅ 可做 |
| 「能玩」验收 | PIE 人玩 / Automation | 默认不 PIE（可授权）；Automation 过滤器只有 `AIAgent.Pawn.Look/Wasd`、`AIAgent.Enemy.Patrol`；`evidence_kind` 无「玩法通关」 | ❌ 缺口 |
| 多新类（Coin / Door / MovingPlatform / HUD 数据） | 批量新建类 | `edit_cpp` 逐类过唯一类门；动作表无「新建类」动作 | ⚠️ 流程可行但重 |

## 缺点说明（四条核心缺口）

1. **表现层域不在动作表**（对应 pending：`material-domain`、`umg-domain`）。`agent/catalog.py` 的十个动作（`compile_project` / `compile_blueprint` / `edit_cpp` / `bind_blueprint` / `place_actor` / `judge_pickup` / `set_pickable` / `move_actor` / `query_actor` / `run_automation_test`）全部是 C++ 与 Actor 放置域。UMG、材质域既没有自动动作（开关也都是 `false`），也没有标准化的人工步骤产出流——蓝图域有 `ue-manual-blueprint-skill` 在开关 false 时把连线步骤写进 `Plan/`，UMG/材质域没有对应技能。L1 理解器遇到「左上角计数」「发光」只能进 `unresolved`，任务书把它们记进「尚未完成」清单后靠人补。
2. **玩法级验收裁判缺失**（对应 pending：`platform-automation`）。`evidence_kind` 只有 `cpp_build / blueprint_compile / editor_assert / automation / manual`。「能玩」= 跳跃可达 + 收齐金币 + 90 秒内开门 + 倒计时归零失败重开，需要 `AIAgent.Platform.*` Automation 族（模拟输入从起点跑到终点，断言金币计数、门开事件、倒计时超时分支），或一次人审 PIE 扇。两样现在都没有——这句话跑完只能记「部分完成」，拿不到「能玩」的测试结果。
3. **关卡组装与保存**（对应 pending：`level-assembly`）。放置动作一次一个，没有「设计图 → 批量布置」链；关卡默认不保存（安全默认正确），缺一条「任务书 + 人授权 `save: true` 一次」的路径。重载关卡即回原样，「能玩的关卡」存不下来。
4. **新类批量流程**。一句需求拆出 3+ 新类，每个都要过 `ue-cpp-plan` 的人审确认门。这是安全设计不是缺陷，但任务书层需要「多类骨架一次生成」的受控动作，否则同一句话要开多轮确认。

## 下一目标路线（按序执行，对应 feature_list 新 pending）

- **阶段 A · `material-domain`**：发光不先碰材质图。给动作表加「材质域只读 + MID 参数覆写」动作（`set_scalar_param` 类，走 `editor_exec` 写闸），`UE_ALLOW_MATERIAL` 维持人审门不变。验收：跑通「给 `BP_Coin` 的 MID 设 `Emissive=5`」这一扇，裁判 `blueprint_compile` 通过。
- **阶段 B · `umg-domain`**：先做 `ue-manual-blueprint-skill` 的 UMG 版——开关 false 时自动产出 `Plan/` 人工步骤文档（新建 `WBP_HUD`、文本绑定、左上 Anchor、倒计时与通关切换），再评估开关 true 时的自动改图。验收：`Plan/` 文档自动生成 + 人按步骤做出 HUD（人工条款）。
- **阶段 C · `platform-automation`**：C++ 写 `AIAgent.Platform.Run` Automation——模拟输入从起点到终点，断言金币计数递增、收齐后门开、90 秒倒计时超时走失败分支。裁判 `automation`，验收：`RunTestsByFilter` 返回 `failed: 0`。
- **阶段 D · `level-assembly`**：设计图 JSON（平台与金币坐标表）→ 批量放置扇 → 一次性人授权 `save: true`。验收：重载关卡后 `query_actor` 复验 Actor 仍在（幂等复验，结论不变才过）。
- **收口**：四条 pending 全过后，把本需求整句作为演示任务跑 `run_windows`，预期合同全绿：C++ 与 Automation 条款由 `cpp_build` / `automation` 改 true；UMG/材质条款视开关状态走 `automation`（自动）或 `manual` + 人审。届时才算拿到「能玩」的测试结果。

# 20261028-1438 — 求解循环：让系统独立接住表外需求

- 背景：20261028-124154 整句 run（给 level3 的 fps 游戏加手榴弹）以能力缺口收口；同日下午由人+agent 手工完成并全部验证通过。两段流程的差分是本计划的全部依据。
- 关联：`docs/upgrade/next-upgrade-plan.md`（D3 动作表膨胀、§4 单一声明源）、`docs/failure/20261028-124154-root-cause.md`、`.cursor/memory/任务记录/2026-10-28.md`
- 性质：RAG 仓库架构升级计划，不改 UE 工程

## 1. 一句话定位

系统今天的问题不是"缺一个手榴弹动作"（那个已经补了），而是**它只有一种解决问题的方法：查动作表**。表外的需求，哪怕每一个子步骤都在现有能力面上，也会整段判死。要补的是第二层：受控求解循环。

## 2. 差分取证：同一天，同一个需求，两条路径

| --- | --- | --- | --- |

关键事实：手榴弹需求**没有任何一个子步骤超出系统现有执行面**——写 C++（apply_spec）、编译（compile_project）、放 Actor（author_map_settings）、收口（run_automation_test）、建 Niagara（monolith niagara.create_system/add_module/…，今天实证 8 次 exec 内完成）。系统输在"不知道能组合"，不是"组合不了"。

## 3. 根因（三个架构层缺陷）

### RC-1 能力模型是静态表，不是能力面视图

`CATALOG` 是人工背下来的技能清单。执行器真实面（monolith 全部 namespace 的 action、official 830 工具）与它之间只有"已声明项"的对账（check_catalog_parity），**没有"未声明项"的发现机制**。Niagara 能力躺在插件里三个月，系统一直以为不存在。D1/D3 点名过表与执行器的集合差，但 parity 守卫的方向是"防谎报"，不是"找遗漏"。

### RC-2 求解路径只有查表一条，失败即终点

`materialize_scopes` 对零窗口范围只有一条补窗路（scope_windows 的关键字规则 + 分解器一次成型），补不出 → capability_gap → 停。与此同时 `agent/graph.py` 里已经有一个完整的求解图骨架（retrieve→plan→execute→build→test→observe→fix，带 retry_limit），**但它只在 `UE_EXEC_MODE=mock` 的注入测试里跑过，从未接到生产执行面**：没有写策略闸门、没有预算约束、`get_build_error` 明文"仍只给网关，不进动作表"——编译错误回灌这条今天最关键的循环，执行面上根本不存在。

### RC-3 学习闭环没有真实轨迹可收

U6 蒸馏钩子挂在成功 run 收尾，但 `learned_skills` 要"槽位形状可路由的成功句"才能路由——表外需求恰恰产不出这种句子。今天人工轨迹（discover 序列、apply_spec 的三对类、测试收口）完全符合可蒸馏形状，却没有容器去收。结果是：每接一个新需求都要人工补 8~13 个声明点（今天补了 8 处，check_backend_coverage 还拦了一次漏报的 COVERAGE 行），动作表只能靠人长。

## 4. 方案：三层求解架构

在不推翻现有闭环（理解器/任务书/人审/裁判/集成矩阵全部保留）的前提下，给"表外需求"加一条受控求解路：

### L0 查表层（现状，不动）

lexicon + CATALOG 命中 → 直接窗。快路径零增量成本，铁律九条在这层原样生效。

### L1 受控求解窗（solve window，核心新增）

范围物化时，零窗口 ≠ 缺口，先给一扇 `solve` 扇（代码侧补窗，同 create_level 的补窗模式）：

```
solve 扇的循环（复用 agent/graph.py 骨架，接真执行面）：
1. 盘点（只读）：按范围动词挑 1-2 个 monolith namespace --discover，
   describe 关键 action；同时 RAG 检索 1 个同模块范式
2. 方案：产出步骤规格——要么全用现有 action 组合，要么带 apply_spec 的 C++ spec；
   必须过 schema 验收与写策略闸（save/pie/allow_writes 唯一来源仍是 session_task.json，不变）
3. 执行：逐原语 exec；遇错读原文，最多重试一次（铁律 4）
4. 编译回灌：apply_spec / edit_cpp 之后强制 build，get_build_error 的错误原文
   作为 fix 上下文进下一轮（今天的 C2039→补 include→C1083→换 include 路径 三连就是这个循环）
5. 收口：有判据（automation / 编辑器断言）→ verify；没有 → 诚实失败
```

**预算闸门（这是"有一定解决问题能力"和"失控 agent"的分界线）**：
- 编辑器调用 ≤8 次/扇、编译轮次 ≤3、模型调用次数 ≤N（config 可调，缺省关：`UE_SOLVER_ENABLED=false`，人开了才走）
- namespace 白名单（今天实证够用的：editor/mesh/niagara/asset；blueprint 系仍走 UE_ALLOW_* 图写闸）
- 预算烧完 / 闸门拒绝 → **降级回 capability_gap**，诚实路径一字不改；同时把整条求解轨迹（尝试了什么、卡在哪、缺哪个原语）写进蒸馏候选——缺口从"一句话"升级成"可复用的失败证据"

### L2 能力面视图（capability surface，基础设施）

- 生成器：跑 monolith 全 namespace `--discover`，落机读 `data/capability_surface.json`（action 名、描述、参数形状）
- 新离线检查 `check_capability_surface.py`：对账 CATALOG——执行器有、规划者看不见的动作 → 自动提名进 `action_candidates`（把 D8 的候选闭环接到真数据源上）；反过来 CATALOG 有、执行器没有 → 现有 parity 报错
- 吸收 next-upgrade-plan §4 的单一声明源（`agent/actions.py`）：新动作的七件套声明点由生成器产出，人只审不写。今天"补一个动作修 8 处"的人工成本归零，动作表才敢"自动生长"

### L3 学习闭环（动作表自动生长，替代"人工补表"）

- L1 成功轨迹（动词 → discover 序列 → 步骤规格 → 判据结果）→ 蒸馏成 learned_skills 条目
- 下次同族动词出现：lexicon 自动提名行（人审一行通过即落表）——今天的 `implement_grenade` 接线如果走了这条路，就是"求解过一次，动作表自己长出来"
- 失败轨迹（预算烧尽、闸门拒绝、判据不过）→ 失败模式库，下次同类需求开局就带避开提示

## 5. 分期与验收

### P0：最小求解闭环（表外需求有第二条路）

1. `agent/solver.py`：受控求解循环 + 预算闸门 + 轨迹落盘 `data/distill/`
2. `materialize_scopes`：零窗口范围先试 solve 扇（`UE_SOLVER_ENABLED` 缺省 false），补不出仍走 capability_gap
3. `get_build_error` 接进执行面：apply_spec/edit_cpp 后自动拉编译错误原文进 fix 上下文
4. eval：`check_solver_budget`（预算烧完诚实失败、不假成功）、`check_solve_gap_fallback`（关开关时行为与今天完全一致）、`check_build_error_loop`（假 Build.bat 注入 error → fix → 过）

### P1：能力面视图与单一声明源

5. `data/capability_surface.json` 生成器 + `check_capability_surface.py` 对账
6. `agent/actions.py` 单一声明 + 七件套生成器；`check_catalog_parity` 改读生成器产物

### P2：蒸馏闭环真跑

7. 成功轨迹 → learned_skills → lexicon 提名 → 人审落表；失败轨迹 → 失败模式库

### 验收基准（用今天真实需求做回归）

把 `lexicon.json` 的手榴弹行临时摘掉（模拟"系统从没见过这个需求"）：整句 `给level3的fps游戏增加道具手榴弹` 应当——L0 未命中 → L1 solve 扇在预算内完成（盘点发现 niagara 命名空间、组合 apply_spec+compile+author_map_settings+automation）→ `AIAgent.Fps.Grenade` 失败数 0 收口 → 轨迹进蒸馏候选。关掉 `UE_SOLVER_ENABLED` 时，行为必须与 20261028-124154 完全一致（诚实缺口）。

## 6. 不做清单（红线，与九条铁律对齐）

1. **不放开全量 schema / list_toolsets / tool_search**——L1 的盘点只走 monolith discover（一次一个 namespace，输出 ~200 字），这是今天实证过的廉价路径
2. **写策略不加特权**：save / pie / allow_writes 唯一来源仍是 session_task.json 与任务书策略；solver 产出方案里的写操作同样要过闸
3. **不放宽裁判口径**：求解成功 ≠ 通过；`verify` 与 `{ok, kind}` 仍是唯一完成证据，`passed` 仍只由裁判改
4. **不做自由 agent**：预算 + namespace 白名单 + 失败即停，三个约束缺一不可
5. **不让 solver 产出的新动作直接进表**：必须走蒸馏候选 + 人审，动作表的写入权在人

## 7. 优先级理由

P0 的第 3 条（build error 回灌）单独拆出来先做：它是今天三连编译迭代的直接等价物，改动面最小（执行面已有 get_build_error，只是不接），且与 UE_SOLVER 开关无关——apply_spec/edit_cpp 执行扇立刻受益。P0 其余三条构成最小求解环；P1 消除人工补表成本（让 L3 有生长土壤）；P2 才让动作表自动生长成为默认路径。

## 0. 三句话结论

1. **“兜不住先问模型”UMG 已经在做**：规划链 `rules → hud-rules → learned → 理解器(模型) → 规划者(模型) → solver` 里，FPS HUD 是唯一跳过模型的；通用 UMG 本来就会落到理解器/规划者。
2. **缺口在“模型产出之后”**：除了 FPS HUD 那条确定性路，其它 `edit_widget_blueprint` 走“discover 猜一个 action”，无只读复核、无“验不过回灌模型改”的闭环——所以看起来兜不住。
3. **脚本 = 通用执行 kernel + 验收 + 沉淀，不是逐控件脚本**：建 Slider/Button/Image/ProgressBar/… 共用同一套原语；控件清单/属性白名单是**数据**，具体值由**模型产的 UI Spec**给。本轮已在 FPS HUD 上真机验证了这套（血条=底条+填充条+数值）。

## 2. 本域「模型-脚本」边界

- **模型**：理解 NL、挑目标 WBP、产 **UI Spec**（要哪些控件/父子/布局/属性）；复核不过时**改 Spec**。
- **脚本**：按 Spec 确定性执行（`add_widget` + `set_widget_property` + slot/anchor）→ 只读复核（`GetWidgets` 控树 + `list_widget_properties` 抽读）→ 结构化失败回灌模型（≤2 次）。
- **路由优先级**：精确契约（rules/hud/learned）命中且整句被盖住 → 免模型直跑；否则先问模型产 Spec → 执行+复核 → 不过回灌修 → 仍不过才暂停点名。**模型永不直接发写工具。**
- **毕业**：稳定可验收的 Spec 用 `remember_route/distill` 沉淀成 learned，`candidate_aging` 退役；novel 永远回模型。

## 3. UMG Spec 草案（模型产出，脚本执行）

```jsonc
{
  "widget_blueprint": "/Game/UI/WBP_Setting.WBP_Setting",
  "parent_class": null,
  "root": "CanvasPanel",
  "nodes": [
    {"id":"Slider_Volume","class":"Slider","parent":"CanvasPanel","anchor":"top_left",
     "position":{"x":40,"y":60},"size":{"x":240,"y":24},"z_order":0,
     "properties":{"Value":0.5,"StepSize":0.1},"brush":{"tint_color":[0.1,0.1,0.1,0.9],"corner_radius":4}}
  ],
  "verify": ["Slider_Volume"]
}
```

**通用执行 kernel 契约**（`build_umg_spec(spec) -> {ok, summary|error(structured), tools, exec_count}`）：
- 与控件无关（数据驱动）：`class` 白名单来自 `list_widget_types`；`properties` 用 `set_widget_property` 通用设；布局用 `add_widget/set_slot_property/set_anchor_preset`。
- 幂等（同 `id` 更新不重建）；父子成环/越界校验期拒；表外 `class` → 结构化“不支持”回灌模型。
- 只读复核：`GetWidgets` 核 `verify` 节点类名 + `list_widget_properties` 抽读属性；失败返回结构化错误供回灌。
- 写闸：`allow_writes ⊇ {AddWidget, RemoveWidget, set_widget_property, SetWidgetProperty, CompileWidgetBlueprint, set_parent}`；`save` 跟任务策略；`allow_umg=true`。

## 4. 分期

- **P0 边界声明 + 防回退（0.5d）**：`check_umg_boundary`——通用 UMG 句必须在 rules/hud/learned 未盖住时进入模型链，不得被宽正则误报成已兜住；FPS HUD 仍走 hud-rules。
- **P1 确定性执行 kernel + 只读复核（2–3d，价值最大）**：`agent/umg_spec.py`（`validate_spec/build_umg_spec/check_umg_spec/SPEC_HINT`）；接成 `edit_widget_blueprint` 首选路径；真机在 probe WBP 建 `Slider+Button+ProgressBar` 冒烟（验完删）。
- **P2 稳定进“理解/规划”（1d）**：给理解器/规划者补 UMG schema/slots；脚本不得以“表里没有”判死，必须先交模型；不可实现→点名暂停。
- **P3 验证驱动回灌修复 + 事件接线（2d，部分）**：结构化失败→回模型改 Spec（≤2）；Spec 扩展 `events` → `BindToEventProperty` 接 `Slider.onValueChanged / Button.onClicked`（不碰游戏逻辑 C++）。
- **P4 图片→UI（契约先行，3–5d+选型）**：`agent/umg_design.py::design_to_spec(image, hint)`，可插拔视觉 provider（先留接口+人工 spec 兜底）；产出仍是 §3 的 Spec → 同一 kernel。
- **P5 沉淀/毕业（0.5d，可并入 P3）**：成功 Spec 经 `remember_route/distill` 毕业；命中仍过 `_clauses_accounted`。

## 6. 风险与取舍

| 议题 | 取舍 | 理由 |
| --- | --- | --- |
| 模型 vs 脚本 | 模型默认参与；仅“精确契约命中且整句盖住”才免模型 | 开放需求不可能全脚本 |
| 假成功 | 模型只产 Spec，永不直接写；写经 kernel+写闸+只读复核 | FPS HUD 教训：能编过≠控件在/属性对 |
| 是否逐控件脚本 | kernel 与控件无关（数据驱动）；控件只是 Spec 的 `class` 取值 | 随组件种类增长不改 kernel |
| 不支持就暂停？ | 先问模型；只有模型也救不回才暂停点名 | 避免“表里没有=判死” |
| 图片→UI | 契约先行、provider 可插拔、先结构后像素 | 避免绑死某视觉模型 |

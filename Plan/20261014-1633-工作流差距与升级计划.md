## 1. 结论

当前工作流是一个「窄闭环」：一句话 → 拆步骤 → 每步跑同一张 LangGraph → 裁判判定 → 记录。它对点了名的窄任务（移 Actor、编译蓝图、改一个类、PIE 探测）已经跑通，最近一次「将ATestPawn的移速提升十倍并测试」两窗全部成功（[data/runs/20261014-162026.md](../../RAG/ue-rag/data/runs/20261014-162026.md)）。

它离「完善的 AI 工作流」差三层，恰好对应两张图：

| 层 | 现状 | 模版图要求 | UI 图要求 |
| --- | --- | --- | --- |
| 预处理层 | 一句话直接拆成 8 种动词级窗口，无范围、无内容清单、无估算、无验收标准 | 按「任务范围 → 尚未完成内容 → 估时 → 依赖 → 集成交付」产出任务书 | 主代理区显示当前指令与审阅轮次 |
| 运行层 | 单线程顺序执行，控制台 echo，断线即失，失败只重试不重规划 | 各范围可分批推进、依赖分批等待 | 窗口状态实时可视、`可续接`、完成区可展开 |
| 验收层 | 每扇一个裁判，全 ok 才算成，报告只有 `.md` 人读格式 | 集成行做正常/拒绝/重复/延迟/断线/未知的矩阵验收，加哈希、日志归档 | 审阅门（附修改）与最终交付状态一目了然 |

升级不动这些底线：单张图、规划者不见 830 个 schema、路径不唯一不猜、裁判不由模型宣布成功、默认不保存不 PIE、编辑器单实例锁。

## 2. 现状：架构与多窗口模式实际是什么

### 2.1 三个入口

[start.bat](../start.bat) 菜单 1 是 `agent/chat.py`（检索一次后回答，不改工程）；菜单 2 是 `agent/run_multi.py`（`plan_sequence` 手写规则拆句，每步跑同一张图，失败暂停等人裁决 s/c/r）；菜单 3 是 `agent/run_windows.py`（多窗口）。[WORKFLOW.md](../WORKFLOW.md) 的分工表与实现一致；`run_agent.py` 留在磁盘不进菜单。

### 2.2 多窗口模式内部

入口链路（[agent/run_windows.py](../../RAG/ue-rag/agent/run_windows.py) 的 `execute_windows`）：

```text
plan_windows(query)
  ├─ 手写规则 _plan_rules 能拆且覆盖 → source=rules
  ├─ learned_routes.json 命中        → source=learned
  └─ 规划者 LLM：只看动作表+这句话    → source=planner
materialize：action 必须在 catalog；槽位解析成唯一类/蓝图/Actor，失败这一窗 realizable=false（暂停）
_ensure_requested_test：句里说「测试」时补一扇 probe_play（PIE）
按 depends_on 拓扑顺序 for 循环逐扇执行（run_task，新 thread_id）
  ├─ 依赖未满足 → 状态「未开始」
  ├─ realizable=false → 状态「暂停」
  ├─ 图动作只跑 1 次（图内部自带 fix 重试）；直连动作按 max_retries 重试
  ├─ EDITOR_LOCK_ACTIONS 持锁执行（threading.Lock）
  └─ 成功扇可向 carry 发布 target_ref / target_in_level，只喂给 judge 类窗口
集成：全部窗口 ok 且数量对齐才成功。不叫模型。
记录：data/runs/<时间戳>.md，按窗口分节 + 集成段
```

动作表（[agent/catalog.py](../../RAG/ue-rag/agent/catalog.py)）只有 8 个动词级动作：`compile_project`、`compile_blueprint`、`edit_cpp`、`bind_blueprint`、`place_actor`、`judge_pickup`、`set_pickable`、`move_actor`。`probe_move / probe_look / probe_play` 只能由 `_ensure_requested_test` 按代码注入，规划者写不出来。

### 2.3 已经对齐、不要推倒的部分

- 规划者上下文有边界（只看动作表和原句），模型不能发明工具、路径和表外动作。这是对的。
- 槽位由代码解析，零条或多条就暂停，不猜。这是对的。
- `learned_routes.json` 写回的是句式和槽位角色，不写死资产名。这是对的。
- 编辑器/编译窗口持同一把锁，因为 UE 编辑器单进程、`cpp_build` 要关编辑器。这是对的。
- 裁判看退出码、`error C`、坐标容差、PIE 探测读数，模型说「好了」不算数。这是对的。

## 3. 两张图要什么

### 3.1 图一：任务预处理拆解模版

模版是一张三列表：**任务范围**（A–E 分区加最后一行「累计集成、验证与交付」）、**尚未完成的全部主要内容**（每区列具体条目，含「代码已有但未接线、未验证」这类现状）、**估时区间**。表下有依赖说明，页脚有总工作量（100–250 小时）、三项免责（任务重叠、估算不构成承诺、不含等待外部的时间）和「目前依赖」（Main/M-UE、M-GO 两类外部依赖，含服务恢复状态）。

把它收敛成机器可验的**任务书 schema**：

```json
{
  "query": "原句",
  "total_estimate": {"min_hours": 100, "max_hours": 250},
  "disclaimer": ["任务之间有重叠", "估算是粗的", "不含等待外部依赖的时间"],
  "scopes": [
    {
      "id": "A", "title": "局外客户端",
      "deliverables": ["登录、选角、建号恢复", "钱包与背包的移动/兑换/同步", "……"],
      "pending_note": "代码已有，缺接线、反馈修正和验证",
      "estimate_hours": [16, 40],
      "depends_on": [],
      "windows": []
    }
  ],
  "integration": {
    "title": "累计集成、验证与交付",
    "deliverables": ["对 Main 版本做验证", "正常/拒绝/重复/延迟/断线/未知 状态矩阵", "补丁与源码/二进制哈希", "日志与报告归档"],
    "estimate_hours": [12, 32]
  },
  "external_dependencies": [
    {"name": "Main/M-UE", "provides": "权威初始化、C3、真事件源"},
    {"name": "M-GO", "provides": "正式契约与部署，接口未登记", "status": "服务 18097 已恢复"}
  ]
}
```

关键点：估时和免责是**记录字段，不是执行预算**。1245 计划写过「不估算小时」，那是对窗口执行说的，保留；任务书里的估算只进文档和人审视野，代码不拿它卡断任务。windows 字段仍由现有 `materialize` 验收，表外动作照旧暂停。

### 3.2 图二：窗口面板

三区一屏：

| 区 | 内容 | 对应实现要拿出的数据 |
| --- | --- | --- |
| 主代理区（顶） | 当前指令（原句）、阶段文案、嵌套的审阅状态（`✅ 审阅 1（GDD 确认）：通过，附三处修改`）、底部 `• 修改了文件` 绿点 | run 级状态 + 人审门结果 + 本次是否有源码/场景改动 |
| 运行窗口区（左下，实线连接） | 标签 `子代理`、`可续接`；任务标题；当前焦点（如「正在分析请求」带旋转符） | 窗口状态机 + 当前图节点（retrieve/plan/execute/build/test/observe/fix） |
| 完成区（右下，虚线连接） | `✓ N 已完成` 计数、闲置检查点文案、`展开` 下拉看历史 | 已完成窗口的 `{ok, summary, elapsed, retries}`，可展开明细 |

实线 = 活跃依赖边，虚线 = 已完成/后台。`可续接` 标签的含义是：这个 run 有落盘的状态，进程重启后能从未完成的窗口继续。

## 4. 距离完善工作流的差距（按层）

### 4.1 预处理层：没有「任务书」这一阶段

现状是句子直接进 `plan_windows`，产出的窗口清单只有 `title / action / slots / depends_on / max_retries`。对照模版：

| 模版列 | 现状 | 差距 |
| --- | --- | --- |
| 任务范围（A–E 分区） | 无。窗口是平铺清单 | 无 scope 概念，无法「先做 A，下周做 B」 |
| 尚未完成的全部主要内容 | 无。只有一句 title | 不枚举交付物；没有「代码已有但未接线」这类现状标注；没有台账来源，说不出「还没完成」是相对什么的 |
| 估时区间 | 无。1245 明确不估算 | 需要把估算作为记录字段引入任务书（不作为执行预算） |
| 表下依赖行 | 有 `depends_on`，但只在窗口级 | 缺 scope 级依赖；缺外部依赖条目（Main/M-UE、M-GO 这种只能等、不能跑的） |
| 累计集成、验证与交付行 | 集成 = 全部 ok 的布尔判断 | 无验收矩阵（正常/拒绝/重复/延迟/断线/未知），无哈希、无归档报告 |
| 页脚免责与总工作量 | 无 | 任务书要自动带 |

根因：规划者的输入只有「动作表 + 这句话」。它既看不到项目状态（哪些已做、哪些没接线），也看不到需求文档，所以不可能枚举出「尚未完成的全部主要内容」。要补的不是放开工具 schema，而是一个受控的摘要输入（见 6.1 边界表）。

### 4.2 调度层：能并行的没并行，能等待的没有等待态

- `execute_windows` 是一个 `for` 循环，全部窗口串行。`EDITOR_LOCK_ACTIONS` 是一把 `threading.Lock`，但单线程下永远无竞争——锁是为并行准备的，并行没来。
- `windows_from_rules` 把规则步骤一律链成 `prev` 依赖，逻辑上独立的窗口也被串行化。
- 没有「等待外部依赖」状态：模版页脚的 Main/M-UE、M-GO 类依赖，只能被当成失败挂起，不能挂成 `等待外部` 且不阻塞兄弟范围。

### 4.3 容错层：只有重试，没有重规划、没有恢复

- 失败只按 `max_retries` 重试同一扇；重试耗尽后没有「把失败结果交回规划者重新拆」的第二循环。
- 集成是全有全无：一扇失败整句失败，哪怕失败扇与别的扇互不依赖；没有部分成功报告。
- 多窗口 REPL 没有人裁决入口：菜单 2 有 `s/c/r`，菜单 3 的 `main` 循环里 `realizable=false` 只打印「暂停」就丢进记录，不能补一次路径再续——单循环的「只问一次 r」规则在多窗口里丢失了。
- 没有回滚：本仓库无 git，`inject_typo` 类试探靠 finally 还原，正式多窗口改动一但写坏没有快照。

### 4.4 持久层：断线即失，没有「可续接」

- LangGraph 的 checkpoint（`agent_checkpoints.db`，按 `thread_id`）存在，但 `run_windows` 从不跨进程读回：跑到一半 Ctrl+C 或断电，已成功窗口的工作全部要靠人重发原句。
- run 状态只有 `.md`（人读格式），没有机器可读的运行状态文件；「可续接」标签没有数据来源。

### 4.5 观测层：只有控制台 echo

- 每扇的进度靠 `echo` 打几行；没有事件流，没有状态机，任何 UI（包括 Cursor 里想看一眼）都只能读最终 `.md`。
- 图二要求的实时状态（正在分析、修改了文件、审阅轮次）在数据上都不存在。
- `rich==15.0.0` 已在 [requirements.txt](../../RAG/ue-rag/requirements.txt) 里，做终端面板不需要新依赖。

### 4.6 验收层：单裁判，无矩阵、无哈希、无归档

- 裁判种类是 `cpp_build / blueprint_compile / editor_assert / automation`，一次一个判定；没有「重复请求不应双发奖励」「断线后不重复执行」这类状态矩阵验收。
- 模版集成行要的源码/二进制哈希、日志归档、报告归档，现在只有一份 `.md`。

### 4.7 记忆层：learned_routes 只记句式，不记进度

- `learned_routes.json` 让同一句式下次直拆，这是对的。但没有任何地方累计「哪些范围做完了、哪些悬着」，下次任务书的「尚未完成」没有台账可读，每次都从零重说。
- 现有的 `documents/` 与 `.cursor/memory/任务记录/` 有原料，但没有聚合成机器可读的按范围进度表。

## 6. 升级设计

总形态：`一句话 → 任务书（人审，可附修改） → 窗口执行（状态面板实时可视、可续接、只读并行） → 集成矩阵验收 → 台账归档`。两个新文件加若干改造，全部在现有进程模型里。

### 6.1 任务书生成器（预处理层）

新文件 `agent/brief.py`。职责：把一句话 + 受控摘要收成 3.1 的任务书 JSON，渲染成模版样式的 `.md`，落 `data/briefs/<时间戳>-<slug>.md`（含同一份 JSON 路径标注）。与大任务的边界（改 1245 §5.4 的表）：

| 谁 | 看得到 | 仍然看不到 |
| --- | --- | --- |
| 任务书生成器 | 原句、动作表、任务书模版 schema、台账摘要（范围级 done/pending，几百字）、`search_ue_project` 的 3 条标题级摘要 | 工具 schema、任何窗口的工具原文、原始检索正文 |
| 规划者（拆窗口） | 同今天：原句 + 动作表（+ 这里的 windows 候选） | 任务书之外的一切 |
| 一扇窗口 | 自己任务句 + 角色工具 + 裁测错误 | 别的窗口 messages、任务书散文 |

估算的生成方式：生成器按每区交付物条数 × 动作类型给区间（新功能宽、只读裁决窄），并自动附免责三行。数字只进文档，执行层不读。

人审门（对应图二 `✅ 审阅 1：通过，附三处修改`）：超过 N 扇（建议 3）或含「新功能/重构」的任务，任务书先停在人审；人可以给文字修改意见，生成器按意见重出一版并记轮次；`确认` 后由代码把 scopes 物化成窗口再进现有 `execute_windows`。窄任务走快路径，不生成任务书。

schema 由代码验收：未知字段丢弃、estimated 超界截断、deliverables 为空的范围暂停。表外内容不进执行，和今天表外 action 一样处置。

### 6.2 窗口状态机与事件流（观测层的地基）

窗口状态：`queued → running → retry → done | failed | paused | skipped`，外加 `revising`（审阅后返工）与 `waiting_external`。run 级状态：原句、来源、审阅轮次、文件改动位。

事件流：`data/events/<run_id>.jsonl`，一行一事件：`run_start / window_state / tool_call / judge / files_modified / window_result / integration / run_end`。`execute_windows` 增加一个 `emit` 回调，现控制台 echo 变成它的一个订阅者，同事件兼写 `.md` 记录（`.md` 保留，人读格式不变）。同时每次 run 落 `data/runs/<run_id>.json` 机读版（P11 的底座）。

### 6.3 终端面板（图二的落地）

`agent/board.py`，用已装的 `rich` Live 做一屏三区，不加新依赖：

- 顶区（主代理）：原句、阶段文案、`审阅 N：通过/附修改`、绿点 `修改了文件`（来自 `files_modified` 事件源：本次有 diff 写入或场景写）。
- 左下（运行窗口）：实线边框、状态标签（`子代理`、`可续接`）、旋转符 + 当前图节点（从 trace 回调拿）、最近一条摘要。
- 右下（完成区）：虚线/暗色边框、`✓ N 已完成`、折叠行，按 `E` 展开选中窗口的 `{ok, elapsed, retries, summary}` 明细页。

### 6.4 持久化与续接（`可续接` 的兑现）

`data/runs/<run_id>.json` 为唯一状态源：窗口状态、窗内 thread_id、已发布 carry 工件、审阅轮次。支撑三件事：

1. `python agent/run_windows.py --resume <run_id>`（或 `latest`）：`done` 窗口直接复用结果；`done` 且图内对话有 checkpoint 的窗口用原 `thread_id` 续上下文；`paused` 窗口进入补路径裁决（见 6.5）。
2. `可续接` 标签 = 存在未终态窗口的 run；面板启动时检索并提示可续接的 run。
3. 工程被写坏的兜底：每个会写源码的窗口开始前记录目标文件字节快照到 `data/snapshots/<run_id>/`，窗口失败且任务无 `keep_source` 时还原（对齐 `inject_typo` 的 finally 语义，推广成窗口级）。

### 6.5 人工裁决对齐单循环

多窗口 REPL 拿回 `s/c/r`：暂停窗口只问一次（`r /Game/...` 或 `r Public/类名.h` 或 `跳过/停止`），规则沿用 `run_multi._decide`。悬空依赖（P5）在 `plan_windows` 验收阶段就报「未知窗口 id」，环依赖（P4）在 `_ordered` 前做一次检测并给出环上的窗口名，两个都不再拖到集成段。

### 6.6 调度升级：只读并行 + 工件传递泛化

- ready-set 调度：依赖全 `done` 的窗口进就绪集；用小线程池执行，写场景/编译类继续过 `EDITOR_LOCK`，纯读窗口并行。`EDITOR_LOCK_ACTIONS` 已分好类，直接用。
- 规则窗口不再假链（P6）：`windows_from_rules` 按 action 读写性判断依赖（编译→强制单线），独立读写之间不虚连。
- carry 泛化（P8）：run 级 `artifacts` 字典，放置/创建/绑定类窗口发布 `{actor_name, ref_path, in_level}` 等键，下游窗口按槽位角色订阅，不再只有一个 `target_ref`。

并行的面板表现：运行区允许多个活跃窗口卡片，实线连接不受影响。

### 6.7 集成矩阵验收与台账（两图的交付闭环）

- 集成不再只是布尔：任务书 `integration.blockers` 决定格局——若失败扇无下游依赖它，整体记「部分完成」，报告按 scope 列出成败（P12）。
- 新动作 `integrate_verify`（进 CATALOG，代码生成而非规划者发明）：按任务书声明跑适用子集——重复请求幂等、拒答路径、延迟窗口、断线重连、未知态恢复，一项一个子判定；集成窗跑完产出：触及文件哈希清单、窗口 `elapsed/retry/token` 汇总、归档路径。
- 台账 `data/ledger.json`：范围级 `done / partial / pending`，由集成结果回写。任务书生成器的「尚未完成的全部主要内容」从台账取，历史任务记录继续追加 `.cursor/memory/任务记录/`，两边不互相替代。

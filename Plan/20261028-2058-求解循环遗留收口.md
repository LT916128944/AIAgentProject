## 1. 遗留清单（按危害排序）

### P0-1 无主写入者：孤儿 cmd 进程绕过全部记录（run 20261028-192951）

**现象**：某个早先 Shell 调用超时转后台后，cmd 子进程没死干净，拿着旧 stdin 文件在 REPL 里自己起了一个真 run——静默跑完 patch + 编译（源码落盘 19:40:26、编译 ok 19:44:37），然后死掉：没写 run md、没进归档、事件流停在 `W1 running`。这次它走对了管线是运气；下次它可能拿着**过期需求**改代码。

**根因**：`start.bat multi` 的进程树生命周期归调用方管，run_windows 对 stdin 的消费没有排他标记；run 记录的 `.json`（status=running）写了但 md/归档只在正常收尾写——中途死掉的 run 留下半截证据链。

**设计**（三层，逐层独立成立）：
1. **stdin 单次消费**：`run_windows` 启动时把 `UE_RAG_STDIN` 指向的文件重命名/标记为已消费（`<原名>.consumed`），再起第二个进程时发现已消费 → 拒绝并以「输入已被另一个进程占用」退出。文件系统原子改名是天然互斥。
2. **run 心跳与孤儿清扫**：run 启动时在 `data/runs/<id>.json` 写 `pid` + 心跳时间戳，窗口收尾刷新；`run_windows` REPL 启动时扫一次同目录超 30 分钟无心跳的 `status=running` 记录，改判 `status=orphaned` 并在 md 补一行「此 run 无主死亡，改动证据需人工核对」——孤儿至少要**留名**。
3. **入口护栏**：`start.bat` 在 `:multi` 分支前检测 `data\runs` 下是否有活心跳 run，有就先提示再放行（人决断，不自动杀）。

**验收**：新增 `eval/check_orphan_run.py`——临时目录里造一条 status=running、pid=当前进程、ts 超 30 分钟的记录 → 断言被改判 orphaned；`.consumed` 原子改名断言。进 offline.yml。

### P0-2 solve 判据兜底：模型省略 automation 过滤器只能诚实失败（185758 / 190218 / 191131 三连）

**现象**：`_SYSTEM` 明说了「最后给一个 automation 过滤器」，四个方案里两个还是省略了 → `no_criteria` 诚实失败，整扇白跑（编辑器调用、patch、编译全做了，就差收口）。

**设计**：收口前 `filt` 为空时，补一次**判据挑选调用**（≤1 次模型预算，复用 `_calibrate_args` 的形态）：输入 = 原句 + 真测试清单 + 本扇做过的步骤摘要，输出只准是一个过滤器或「无」。输出仍必须命中 `automation_filters` 的真清单（编造整条丢）；仍挑不出 → 维持 `no_criteria`，不放宽。

**验收**：`check_solver_patch.py` 加两组断言——方案省略 automation 但模型补选成功 → 收口走真过滤器；补选输出编造 → 维持 no_criteria。

### P1-3 describe 吃掉一半编辑器预算（200112：6/8 次花在执行前）

**现象**：盘点 1 + automation 1 + describe 4 = 6 次预算在执行前烧掉，5 步方案跑到第 3 步「预算烧尽」。describe 与 discover 同级（只读元数据），却占执行预算。

**设计**（二选一，先 1 后 2）：
1. **缓存优先**：`pipelines/export_capability_surface.py` 导出的 `data/capability_surface.json` 增加 params 形状字段；`describe_actions` 先查缓存（按 `ns.action` + 后端指纹），miss 才真 describe。编辑器在线时由人重跑导出刷新。
2. **预算语义分离**：`Budget` 加 `meta_calls` 类目（discover/describe/list_automation_tests 共享小额度，缺省 12），执行调用继续走 `editor_calls`。改动要同步 `check_solver_budget.py` 的断言口径。

**验收**：check_solver_patch 加「缓存命中不烧预算」断言；若走方案 2，check_solver_budget 全量断言改写后仍绿。

### P1-4 补扇不相关：solve 失败后模型补出 implement_shooter 顶班（183641 / 194552）

**现象**：W2（solve）失败后，run_windows 让模型补一扇，补出 `implement_shooter`——动作存在、能跑通，但与「改射速」毫无关系，浪费一扇并制造「有扇在跑」的错觉。

**设计**：补扇 prompt 已带失败原因；再加一道**覆盖对账**——补扇动作的声明能力必须与该范围 unmet 交付项有字二元组重叠（复用 `_uncovered_deliverables` 的同一套），对不上就不补，集成按「窗口失败」诚实收口。补出的扇在 run md 里标 `来源：补扇`。

**验收**：`check_harness.py` 或新 check：solve 失败 → 补扇对不上 unmet → 不补、集成失败带原因；对得上 → 补。

### P2-5 台账 done 必须绑改动证据（190722 假 done 污染过下一句任务书）

**现象**：集成把假成功范围写成台账 `done`，下一句同域需求的任务书直接引用「改值已 done」，人审看到的现状就是错的（191314 实测）。

**设计**：integration 写台账 `done` 行时，校验该范围存在**改动证据**（`spec_files` 非空且编译裁判 ok，或 write 类编辑器裁判 `{ok, kind}` 对上）；缺 → 状态记 `partial` 并把缺口写进 pending，绝不写 done。守卫层（read_only_plan/write_skipped）拦住假成功后，这一条是台账入口的最后一道。

**验收**：`check_integrate_verdict.py` 扩一组：有窗口成功但无改动证据的范围 → 台账不得出现 done。

### P2-6 改动判定词表是白名单，覆盖面靠观察补

**现象**：`_CHANGE_IMPLYING_RE` 现在是「改/调整/设置/倍/实现/新建/创建/删除/换成/提高/降低/加速/加上/去掉」。「把门打开」「把灯关了」这类状态变化动词不命中 → 纯验收方案不触发 read_only_plan 守卫。

**设计**：不抢着扩词表（误扩会把「打开编辑器」误伤）。改用失败模式库兜底：distill_trajectory 对 `read_only_plan` 收影子条目；人审失败模式时把漏掉的动词补进词表并加对应用例。词表改动必须带 `check_solver_patch` 用例。

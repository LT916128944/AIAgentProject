## 1. 结论

动作×后端矩阵已经在 CI 里，不生成第二份 JSON。DeepSeek 点名要补的 `place_batch`、`set_scalar_param`、`remove_batch`、`move_actor`、`open_level`、`implement_shooter`、`implement_grenade`、`create_level`、两个 Widget 动作，在 `COVERAGE` 里都是 `both`。

剩下的洞是两处：`judge_pickup` 和 `set_pickable` 标了 `partial`，因为 monolith 没有 `get_properties` / `set_properties`；带 props 的设计图对已经放进关卡的实例不能复读、不能重写，幂等重跑会在执行扇才失败。回滚要加的是五类确定故障，不是一个号称 Undo 的新模块，也不是 100 次随机注入。

## 2. 现在实际怎么走

`eval/check_backend_coverage.py` 做两件事：`agent/sequence.py` 里没有 monolith 分支的 `exec_tool` 原语，必须出现在 `core/monolith_bridge.py` 的 `MAPPED` 或 `UNSUPPORTED`；`agent/catalog.py` 的每个动作在 `COVERAGE` 里有一行，取值只能是 `both`、`partial:原因`、`official_only:原因`。

`UNSUPPORTED` 里和本计划有关的两条：

- `get_properties`：monolith 没有实例属性读入口
- `set_properties`：monolith 没有实例属性写入口

`place_batch` 在生成实例时可以写 props。已存在的实例走不到这条路径。`progress.json` 的风险写明：幂等重跑要先 `remove_batch` 清掉再放。这个失败发生在执行扇。

`agent/prop_snapshot.py` 与 `eval/check_write_rollback.py` 已经钉住：scalar 覆写前记旧值，restore 写回；`place_batch` 新建的 Actor 登记进 props.json，restore 按名删除唯一实例；同一实例登记两次只删一次；名字命中不是恰好一个就不删。`feature_list.json` 的 `editor-transaction` 仍是 pending，笔记写「没有编辑器 Transaction/Undo」。

## 3. 改法

### P1 — partial 在拆句就暴露

`COVERAGE` 保持这两行 `partial`，原因文字保留。增加一份拆句要读的集合，放在 `check_backend_coverage.py` 同文件里再导出，或放在 `monolith_bridge.py` 旁边的一个常量：当前后端是 monolith 时，依赖 `get_properties` 或 `set_properties` 的窗口不得进入执行列表。

`agent/plan_windows.py` 在出窗口之后看这个集合。命中则丢掉该窗口，把原句里对应的半句留在 `unresolved`，并写一行到当次 `Plan/` 说明：monolith 读不到或写不了实例属性，人要先清实例再放置，或者改走官方后端。不生成一个会在执行期被拒的窗口。

`place_batch` 生成时写 props 的路径保留。限制只针对「实例已经在关卡里，还要读或改它的属性」。

验收加在 `check_backend_coverage.py`：monolith 下含 `judge_pickup` 或依赖 `set_properties` 的 `set_pickable` 计划结果里没有执行窗口，`unresolved` 非空。官方后端下这两条仍可进窗口。不新开 `check_backend_matrix.py`。

### P2 — 五类故障，每类一条样例

扩展 `agent/prop_snapshot.py` 的记录，使每次写前快照带：动作、目标 ref、逆操作、幂等键。同一 ref、同一幂等键的第二次回滚直接跳过，这条和现有「登记两次只删一次」对齐，不另写规则。

`eval/check_write_rollback.py` 增加五条，全部用临时目录和假的 exec，不连编辑器：

1. 写属性调用在中途返回失败：scalar 恢复到快照里的旧值。
2. 编译失败：快照仍在，不被标成已消费。
3. 保存失败：快照仍在，关卡差异记录留在快照目录。
4. 执行器返回连接失败：restore 再失败时写 `manual_intervention`，不继续下一条逆操作。
5. run 记录被 `sweep_orphan_runs` 改判 orphaned 之后，下一次续接先按快照逆序恢复，再允许新的写。恢复本身失败则停，并写 `manual_intervention`。

冲突：同一 ref 有两份快照且旧值不一致，不执行任何一份，写 `manual_intervention`。

有编辑器原生 Transaction 时才标 `native`。本计划不发现、不调用这种 API。记录里的方式字段写 `compensating`。`editor-transaction` 保持 pending。

不设「100 次随机注入、成功率 ≥99%」。五条确定样例全过即过。随机次数证明不了逆操作写对了。

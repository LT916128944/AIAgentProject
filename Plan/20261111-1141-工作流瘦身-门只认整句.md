## 1. 结论

菜单 3 已经能把「编译工程」这类整句收成零模型窗口，也能在动作表外开一扇受控求解扇。它接不住新需求，是因为**词命中会在问模型之前把整句领走**，领走之后半句不再出现。求解扇只在「一个窗口都没有」时才开口，开口之前理解器和任务书都只许点动作表里的名字。

瘦身不是再加一道门。是让现有的门只认自己盖得住的整句；盖不住的半句只问一次模型，问的时候不再把同一份动作表贴两遍。

## 2. 现在菜单 3 实际怎么走

`start.bat` 菜单 3 进 `agent/run_windows.py` 的 `_run_query`。拆句在 `plan_windows`，顺序是固定的：

```text
原句
  → L0 手写规则          _plan_rules + _rules_cover 全中：0 次模型，source=rules
  → FPS HUD 规则         hud_windows 命中：0 次模型，source=hud-rules，并跳过人审
  → 已学句式             match_learned：0 次模型，source=learned
  → L1 理解器            一次模型调用，goals 只能是动作表里的名字
  → 表外 goal 被丢掉     intent.py validate_intent：没有剩下的 goal 就整段作废
  → 老规划者             再一次模型调用，materialize 仍只收动作表
  → 代码补窗             场景闸、诊断句、句尾「打开 / 测试」
  → 窗口全是暂停牌       且 UE_SOLVER_ENABLED：补一扇 solve
  → 否则出任务书         生成器再次被要求「只能用动作表」
```

动作表（`agent/actions.py` 的 `ROWS`）是规划者能点的全部名字：启动编辑器、编译、改一个 C++ 类、摆 Actor、HUD、射击、手榴弹、两条 HUD 复核等。`implement_shooter`、`implement_grenade`、`check_fps_hud` 是按句子长出来的专用动作，不是通用原语。

求解扇（`agent/solver.py`）是今天唯一允许模型组合原语的地方：discover → 定位源码 → 步骤规格（盘点里的原语或对已有文件做一处替换）→ 编译回灌 → Automation。预算缺省是编辑器 8 次、元数据 12 次、编译 3 轮、模型 6 次。它挂在两条窄入口上：快路径一个可执行窗口都没有，或任务书范围物化后仍是零窗口。理解器只要点中一个表内动作，求解扇就不会被叫到。

裁判、写闸、一次只连一个编辑器后端，这三样继续有效。本计划不改它们。

## 3. 死板的证据（离线，没有跑菜单 3）

工作目录 `RAG/ue-rag`，只用规则函数，没有调用模型，没有连编辑器。

| 原句 | 规则结果 | 模型有没有机会看见后半句 |
| --- | --- | --- |
| `编译工程` | `rules_cover=True`，一扇编译 | 不需要。这句就该零模型 |
| `在 L_NewTest 给玩家加冲刺：按住 Left Shift 时最大行走速度乘 1.8，松开恢复，冷却 1.5 秒，屏幕左下角显示剩余冷却。` | 规则、HUD、诊断、已学句式都是空 | 会进 L1。L1 仍只能点表内动作；「改速度 / 改输入 / 改冷却」都不是动作名。点中 `edit_cpp` 或 `edit_widget_blueprint` 之后，求解扇不再开口 |
| `给 FPS 加血条和子弹显示，同时给玩家加滑铲` | `is_fps_hud_request=True`，`hud_windows` 直接给出 `create_widget_blueprint → edit_widget_blueprint → check_fps_hud` | **没有。** `hud_windows` 排在理解器前面。`_needs_brief` 对 `source=hud-rules` 且窗口都可跑时跳过人审。滑铲被整句丢掉 |

第三条就是「超过这条规则的理解能力，却不去问模型」。`eval/check_fps_hud.py` 把「整句 FPS HUD 必须零模型」钉成绿，测的是纯 HUD 句（血条、子弹、手雷、载具）。它没有断言「句子里还有别的玩法时必须放行」。所以这条吞句在离线套件里是合法的。

`_rules_cover` 里已经有「半句没被接住就不要当强命中」（`_clauses_accounted`）。HUD 规则和已学句式不走这道检查，排在它前面或旁边。

需求词表 `_DEMAND_RE` 只认「实现|逻辑|随机|功能|需求|行为」。冲刺、滑铲、改速度都不在里面，不能把一次弱命中打回理解器。

## 5. 改法

三刀。先改判定，再并掉重复的模型调用，最后才删文档里的重复叙述。

### P1 — 门只认整句

命中 `rules`、`hud-rules`、`learned` 之前，用现成的 `_clauses_accounted` 看原句。有半句对不上这条路径声明的动作，这条路径返回空，交给后面的模型。不新写一套玩法词典。

`hud_windows` 对 `check_fps_hud.py` 里的那句纯 HUD 仍返回今天的五扇链。`给 FPS 加血条和子弹显示，同时给玩家加滑铲` 必须返回 `None`。

`_needs_brief` 的跳过人审只保留「返回的窗口已经盖住整句」的来源。盖不住就不要标 `hud-rules`。

验收只改 `eval/check_fps_hud.py` 已有的那条：纯 HUD 句仍然零模型；多一句玩法时 `hud_windows` 必须是 `None`。不新增 `check_*.py`。

### P2 — 表内计划盖不住时，只问一次

理解器仍然先跑，仍然只许点动作表。变的是失败之后：

- 今天：理解器失败 → 规划者再点一遍动作表 → 暂停牌 → 有时才进求解扇。理解器「成功」但半句在 `unresolved` 里时，求解扇根本不看。
- 改完：理解器的 goals 盖不住原句（`unresolved` 非空，或 `_clauses_accounted` 对 goals 为假）时，不再调用规划者，不再用残缺 goals 直接执行。改为调用求解扇已有的那一次方案生成（盘点名、源码定位、步骤规格、编译回灌、Automation）。人审留一次：方案里有写 C++ 或改关卡才出任务书，任务书引用这份方案，不再要求生成器「只能用动作表重写一遍」。

预算数字不动：模型 ≤6、编辑器 ≤8、编译 ≤3。写闸仍只读任务书和 `session_task.json`。没有判据就诚实失败，不许用旧测试通过代替没写的代码（求解扇里已有的 `read_only_plan` / `write_skipped`）。

`UE_SOLVER_ENABLED` 维持现状：本机开着才走这一问；关着时盖不住的半句停在缺口，不静默执行残缺窗口。

### P3 — 提示和「当前系统」变短

P1、P2 的行为稳定之后再改字：

- `understand.py` 与 `brief.py` 不要各贴一份完整动作表。任务书已经拿到候选窗口时，提示里只留这些窗口的动作名和槽位。
- `WORKFLOW.md`「当前系统」收成和 `README.md` 入口表同一量级的短节：一个后端、四条菜单、门只认整句、求解扇的预算、三条仍 pending 的 `feature_list` id。求解扇内部守卫留在 `solver.py` 文件头。按 `ue-doc-sync` 只改被这节引用到的 `README.md` 和 `RAG/ue-rag/README.md` 句子，不改沿革。
- `progress.json` 的 `next_action` 改回一句「下一次从哪条 pending 做起」。现在这一字段是整段升级散文，开工 `resume_context.py` 会把它打出来。

不删 `fps_hud.py`、`implement_shooter`、`implement_grenade`。它们继续服务已经落地的句子，只是不再当新句子的模板。

## 8. 确认后怎么验收

离线（P1 结束就要绿，不连编辑器）：

1. `编译工程` 仍是 `source=rules`，`understand_called=False`。
2. `check_fps_hud.py` 的纯 HUD 句仍是五扇链。

在线只做一次，放在 P2 之后、由人看着任务书确认再跑：菜单 3 输入冲刺那句。通过标准是运行记录里出现一次方案生成，并且方案文本里同时有速度、按键、冷却三件事，或者明确写出哪一件做不到。不允许在没有这三件事的情况下用 `check_fps_hud` 或一条旧 Automation 收成成功。

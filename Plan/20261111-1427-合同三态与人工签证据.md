## 3. 改法

### P1 — 先回放 20261021-195220，再决定要不要加反例

开工第一件事只读这份 run 的决策字段（窗口动作、条款 id、判词的 ok/kind/window）。路径在 `RAG/ue-rag/data/runs/` 或 `data/archive/`，按 run_id 找，不读 `.umap`。

用当前的 `build_criteria` + `apply_judge` 回放。条款保持 false，就在 `check_criteria_binding.py` 的文件头记一句「已由 180955 的收窄盖住」，不加新用例。有条款被翻绿，就把该形状收成同文件里的第二条断言。不新开 `check_contract_soundness.py`。

### P2 — 翻牌写入证据哈希

`apply_judge` 翻成 passed 时，在该条款上写 `evidence_sha1`。哈希输入是判词的 `ok`、`kind`、`window`、`summary` 四个字段的稳定 JSON。翻牌条件仍是：判词 `ok` 为真，`kind` 与条款一致，`window` 在条款的 `windows` 里。synthetic 判词继续只放行「证明窗口恰好只有它自己」的条款，这条已经在 180955 的回归里。

回放时哈希对不上，该条款回到 false。验收加在 `check_criteria_binding.py`：合法翻牌带哈希；改一个 summary 字节后回放，条款是 false。

### P3 — 整句三态

在 `agent/harness.py` 增加一个纯函数，输入是窗口结果和条款，输出 `ok`、`partial`、`failed` 之一：

- 任一执行窗口失败，而条款却全是 passed：`failed`。这是 180955 的整句口径，不只是单条条款。
- 有 `manual` 条款且没有对应人签：`partial`。其余非 manual 条款即使全过，也不是 `ok`。
- 全部非 manual 条款 passed，没有失败窗口，没有未签 manual：`ok`。

`run_windows.py` 的收尾退出码调用这个函数。`partial` 的退出码与 `failed` 区分开，并在 run 记录里写这个字符串。模型输出的「成功」「已完成」不参与这个函数。

验收：`check_criteria_binding.py` 增加「窗口失败且条款全过 → failed」。`eval/check_harness.py` 增加「有未签 manual → partial」。两处都用临时条款，不改 `feature_list.json`。

### P4 — 人签只翻 manual

新增 `agent/manual_attest.py`：

- 读 `data/attestations/<criterion_id>.json`。字段：`criterion_id`、`person`、`signed_at`、`evidence_path`、`evidence_sha1`。
- `evidence_sha1` 是证据文件字节的 sha1。文件不存在、字段缺、哈希不符：该条款保持 false。
- 只允许 `evidence_kind=manual` 的条款走这条路径。`editor_assert` 等条款拒绝人签。
- 人签文件由人写。函数不调用模型，不根据聊天文本生成。

巡逻这一条的步骤文件：从现有人工说明抽出一份 `Plan/patrol-presentation.json`，字段固定为蓝图、事件名（`OnPatrol`、`OnChase`、`OnMeleeAttack`）、引脚、人要核的现象。生成可以用一次脚本，脚本不写 attestation，不改 `passed`。

离线检查用临时目录证明三态：无文件 → false；哈希被改 → false；哈希相符 → 该临时条款 passed。仓库里的 `patrol-presentation` 保持 pending，直到人真正签了一份、并且人另行决定让检查改 `feature_list.json`。本计划的实现不写这个 passed。

## 0. 一句话结论

**全仓的工具层极宽（52 个 Toolset），但流水线的“一等动作表（`agent/catalog.CATALOG`）只有 26 个”。凡是没有一等动作的域，需求今天都落到通用 `solve`（受控求解：模型 discover→describe→exec 原语，只有 automation 收口）——就是“模型接管了、但没有确定性执行内核 + 只读验收 + 回灌修复”。`CATALOG` 的 26 个动作就是“已经被脚本兜住”的那一圈；圈外的域，都是本类缺口。**

## 1. 共享边界（与 UMG rev2 同一套，全模块通用）

> **模型定 WHAT，脚本定 HOW + 验收，`learned` 是沉淀桥。**

| 职责 | 归谁 | 备注 |
| --- | --- | --- |
| 理解自然语言、挑目标、拆意图、产该域 **Spec** | **模型**（理解器/规划者） | 现状本就会问模型，见 `plan_windows._plan_windows_body` 链路 |
| 按 Spec 确定性执行（建/改/连/设） | **脚本（该域执行 kernel）** | 必须幂等、可复现 |
| 写编辑器前放行（allow_writes / save / pie / `UE_ALLOW_*`） | **脚本（写闸）** | 不交给模型 |
| 只读复核（对象在不在/属性对不对/节点连对没/编译过没过） | **脚本** | 假成功的唯一防线 |
| 复核不过 → 改方案 | **模型（回灌修复，有限次）** | 本次要补的关键闭环 |
| 稳定可验收的方案沉淀成免模型快路 | **脚本（learned/蒸馏）** | novel 永远回模型 |

**路由优先级（全模块一致）**：`精确契约命中且整句被盖住 → 脚本直跑`；`否则 → 问模型 → 产 Spec → 脚本执行+复核 → 不过回灌模型修(≤N) → 仍不过才暂停点名`。**模型永不直接发写工具，只产 Spec。**

## 3. 统一交付模板（每个分模块计划都按这个形状写）

每个域落地都产出四件套，缺一不算“兜住”：
1. **Spec 契约**（该域的结构化描述：对象/节点/连线/参数/层级/绑定）。
2. **确定性执行 kernel**（Spec → 原语调用；幂等、写闸、结构化失败）。
3. **只读 verifier**（复核 Spec 的每条断言：存在性/属性/拓扑/编译）。
4. **回灌修复闭环**（verifier 的结构化错误 → 模型改 Spec → 重跑，≤2 次）。

外加：
5. **路由**：该域需求稳定进“模型产 Spec”链；`_clauses_accounted` 盖不住就退回模型，不静默。
6. **沉淀**：成功且稳定的 Spec 用 `remember_route/distill` 毕业成免模型快路；`candidate_aging` 退役。
7. **离线守卫**（`eval/check_<域>_spec.py` 等）：打桩、不连编辑器；登记 `offline.yml`。

**沉淀与守卫是为了“兜住”，不是为了“全脚本化”**：模型永远是 novel 需求的主力，脚本只固化“已被证明稳定可验收”的那部分。

## 5. 共享守卫（每个域都要有，按 §3 第 7 条）

`check_<域>_boundary`（模型主力不误报）/ `check_<域>_spec`（kernel 确定性·幂等·白名单·复核）/ `check_<域>_repair`（回灌修复有上限·终态可解释）/ `check_<域>_route`（稳定进链、不支持点名暂停）。全部登记 `RAG/ue-rag/.github/workflows/offline.yml`。

## 6. 施工顺序建议（跨域）

> 动手前先读 [UMG 计划](20261117-1545-UMG需求边界扩展计划.md)：它是这套「Spec→kernel→verifier→repair→graduation」的**参考样板**，图域都可照它改“节点/控件白名单”。

1. **先蓝图**：图节点/连线的“Spec + kernel + 复核”是动画蓝图、材质图、Niagara 蓝图、ControlRig 的共同地基——蓝图域做好，其它域能复用大半。
2. **再材质 + Niagara**：两者工具集清楚、对象独立、验收直观（读回参数/节点/系统栈）。
3. **后动画/Sequencer/AnimBP**：带时间轴与绑定，验收要读回 track/key/binding。
4. **后处理最后**：无专用原语，走“属性路径”验证（读回 PostProcessVolume/Camera 的设定值）。
5. **C++**：不重写，做“Spec 化 + 回灌边界收口 + 覆盖面补齐”。

> 一句话：**这轮不是把 52 个 toolset 挨个写脚本，而是给每域补“Spec→kernel→verifier→repair→graduation”这一条通用流水线；模型负责把开放需求变成 Spec，脚本负责把它变成可信、可复验、可沉淀的编辑器改动。**

## 1. 结论

闭环已经能做窄任务：移动一个点了名的 Actor、编译一张点了名的蓝图、给 `TestActor.cpp` 打一个已知错再改回来。它处理不了组合句，是因为 `plan_sequence` 用整句正则把话收成少数几个模板，模板对不上就暂停。模型几乎不参与拆句。

「编译工程后启动 UE 编辑器，然后测试 ATestActor 能否被 ATestPawn 拾取」需要四件已经分别存在的事：编译工程、启动编辑器、把资产放进当前关卡、按源码里的拾取条件做只读判断。现在这四件事没有被收成一条可执行序列。

下一阶段保持「工作流」：步骤种类由代码规定，路径对不上就停，裁判不由模型宣布成功。要补的是步骤种类和参数绑定，不是把 830 个 MCP 工具交给自由 Agent。

## 4. 现在的架构，死板出在哪一层

两条入口共用检索库和 `editor_exec.py`。日常 Cursor 对话不调用 `run_task.py`。`start.bat` 的三条是：检索后回答、单 Agent 图、多 Agent 序列。

```text
一句话
  → plan_sequence          正则模板。对不上就暂停
       ├─ 改唯一 C++ 类并 cpp_build
       ├─ 编译唯一 BP_
       ├─ 把唯一 Actor 移到句中坐标
       ├─ 创建蓝图（缺目录则 r）
       ├─ 放进场景（沿用上一格路径，固定 (0,0,100) 贴地，不保存）
       └─ 给实例写上拾取标签再查一次
  → 能跑的步骤才进入 LangGraph
       retrieve → plan → execute → build → test → observe → fix
  → judge.py 当裁判，模型不能自己说成功
```

「多 Agent」是同一张图换提示和工具子集（监督者 / C++ / 编辑器 / 裁判），不是各自隔离上下文的工人。这个决定在 [Plan/20261012-1706-多Agent自动闭环与分层检索.md](20261012-1706-多Agent自动闭环与分层检索.md) 里已经定过，下一轮不要拆成第二套图。

已经对齐、不要推倒的部分：

- 官方 Unreal MCP 是编辑器出口。工具卡片不带 schema，`--schema` 一次只开一个。
- 路径不唯一就不猜。这个原则保留，改的是「什么必须唯一」。
- `save` 默认 false，`pie` 默认 false，`UE_ALLOW_BLUEPRINT` 默认 false。
- 裁判看退出码、`error C`、位置容差、Automation 的 `failed` 计数。模型说「好了」不算。
- `--query` 不是 Cursor 里每句话的默认动作。

死板来自下面几条，它们叠在同一句上：

| 问题 | 现在的规则 | 这句上的后果 |
| --- | --- | --- |
| 整句一个槽位 | 出现 C++ 类名时，全句只能对应一个类 | 测试句里的两个类被当成「改哪一个类」 |
| 动词太少 | 编译 = 改那个类；启动编辑器 = 改完源码的副作用 | 「编译工程」「启动编辑器」没有步骤 |
| 场景动作靠四个词 | 没写「放进场景」就不放置 | 测试拾取不会先把人和物放进关卡 |
| 检查会改现场 | `check_pickup` 先写入标签再查询 | 通过不能说明原来能否拾取 |
| 绑定不看索引 | 创建/放置/拾取一律先要人填目录 | `/Game/BP_TestPawn` 已经在库里也不会用 |
| 模型兜底仍进同一套函数 | `_from_model` 只许四个 `kind`，然后调用 `_try_cpp` / `_try_editor` | 规则失败后，模型也写不出这句的步骤 |
| 题集里没有组合句 | 默认三条是移 Cube、编译 `BP_Gun`、注入编译错误 | 这种句子坏了，`run_eval.py` 仍然全绿 |

Cursor 日常链可以读 `TestPawn.cpp` 再调 MCP，所以人会觉得「这句话本来就该能做」。命令闭环在进图之前就被模板拒绝了，读不到这段拾取代码。健壮性差的是监督者，不是编辑器工具不够。

## 5. 网上主流架构，和这里的对应关系

对照的是分层，不是再引进一个产品。[周计划.md](../周计划.md) 第 2.3 节和第 12 节已经明确不做复杂多 Agent、不做微调、不新造一套 UE MCP。

### 5.1 工作流和自由 Agent 分开

Anthropic《Building Effective Agents》把系统分成两类：工作流是代码规定调用路径；Agent 是模型自己决定下一步用什么工具。能预测步骤时用工作流，步骤随输入变化且无法事先写死时才用 Agent。编排器-工人是工作流的一种：编排器按这句输入拆子任务，工人执行，编排器汇总。评估-优化是另一条：生成和裁判分开，裁判有明确标准。

来源：<https://www.anthropic.com/engineering/building-effective-agents>

本仓库选工作流是对的。UE 编辑器是单进程，Live Coding 会锁住模块 DLL，不能学云端编码助手那样开多份沙箱并行改同一工程。问题是工作流的代码路径只覆盖了「一个类、一个坐标、一张蓝图」，组合句的步骤其实可以预测，只是没写进路径。

### 5.2 编码助手的套件：短规则、按需技能、钩子、隔离子任务、计划门

Claude Code 的用法是：`CLAUDE.md` 保持短；技能先看见名字和说明，命中再读正文；钩子在工具调用前后做确定性拦截；子代理用单独上下文，只把摘要交还主会话；计划模式只读，人确认后才放开写。

来源：<https://claude.com/resources/articles/steering-claude-code-skills-hooks-rules-subagents-and-more>，以及 2026 年对 Claude Code 设计空间的分析 <https://arxiv.org/abs/2604.14228>

本仓库 Cursor 侧已经有短的 `AGENTS.md`、按 description 加载的 Skill、`editor_exec.py` 的写拒绝，以及一条拦改图的 hook。命令闭环侧的「多 Agent」没有隔离上下文，技能卡片只有 name / description / path，`plan` 只塞一张说明。这些是以后的事。这句失败不需要先做子代理。

### 5.3 给模型的动作要少，反馈要来自真环境

SWE-agent 的结论是：模型外面放一层窄的命令面（搜索、查看、按行改、执行），格式不对就拒绝并返回错误，观察结果来自命令真的跑过。来源：<https://arxiv.org/abs/2405.15793>

Open SWE 一类系统把活分成调查、在隔离环境里改、用真测试验收、再交付。验收读的是测试结果，不是代理自己把断言改成真。来源：<https://github.com/langchain-ai/open-swe>

LangChain 在 2026 年不再维护 `langgraph-supervisor` 这个包，建议主代理把工人当成工具来调，工人只交回摘要。来源：<https://docs.langchain.com/oss/python/migrate/langgraph-supervisor>

和本仓库的差距：动作面已经够窄，窄过了头，缺「编译整个工程」「启动编辑器」「按资产放入关卡」「只读询问能否拾取」。`check_pickup` 先改标签再查询，属于代理自己制造通过，和「测试当裁判」相反。

### 5.4 不要照搬的部分

| 主流里常见 | 这里不采用 | 原因 |
| --- | --- | --- |
| 长时自主、多虚拟机 | 不做 | 编辑器单实例；周计划第 2.3 节已放弃复杂多 Agent |
| 模型当唯一裁判 | 拾取这种有源码条件的，用确定性判断 | 条件是标签加 1 米，调用函数或读属性就够 |
| 把全部工具 schema 放进上下文 | 继续用卡片 | 官方索引 52 个工具集、830 个工具 |
| 一上来做计划模式产品 | 命令闭环先把这句的步骤跑通 | Cursor 侧已有 `.cursor/memory/plans/` 门禁 |

Anthropic 的多智能体研究系统还强调：路径不固定时，评测看结果是否达到，不要规定唯一走法。来源：<https://www.anthropic.com/engineering/multi-agent-research-system>。这句的走法可以规定。评测看的是「编译是否执行、编辑器是否起来、裁决是否只读且与源码一致」，不看模型有没有说「可以拾取」。

## 6. 目标行为

同一句，下一轮做成下面这条序列。任务成功的意思是序列跑完并给出裁决。裁决可以是「不能拾取」。把 Actor 改成可拾取是另一句，例如「让 ATestActor 能被 ATestPawn 拾取」，那一句才允许写属性。

```text
编译工程
  不改源码。编译前若编辑器开着，沿用现在的关闭。
  裁判仍是 cpp_build：退出码 0，日志没有 error C / fatal error。
启动编辑器
  这句写了「启动」，编译通过后调用已有的 launch_editor，等到 MCP，最多 120 秒。
  不要求这次写过源码。
绑定
  拾取者 = ATestPawn，物体 = ATestActor。两个类是两个槽，不是冲突。
  蓝图：句中路径优先；否则索引用唯一命中。
  现在 Pawn 能唯一落到 /Game/BP_TestPawn.BP_TestPawn。
  Actor 在索引里没有蓝图，这一格暂停，只问一次 r /Game/.../BP_名字。
  人跳过 Actor 格时，后面的放置和裁决不要假装已经测过。
放入当前关卡
  两个实例都有了路径或已经在关卡里，才放置缺的那一个。
  两者距离小于 100 uu。不保存关卡。不 PIE。
只读裁决
  读物体的 bAllowPickup、bCanBePicked、Tags，按 CanBePickedByPawn 的合取。
  再读两者位置，距离大于 100 uu 则这只 Pawn 拾不到。
  不调用 set_properties。不给实例补标签。
输出
  「能」或「不能」，带上没满足的那一条（开关、标签或距离）。
```

「让它能被拾取」以后再做：先只读裁决，不够再写 `bAllowPickup` / `bPickable`（写入会走现有的 `SetAllowPickup` / `SetPickable` 语义，而不是直接改 `Tags`），然后用同一套只读裁决再查一次。本文件的第一轮不写属性。

## 7. 实施顺序

工作目录 `E:\UEProject\AIWork\RAG\ue-rag`，Python 用该目录 `.venv`。不要把 `--query` 接到 Cursor 每句话上。不要启动 PIE。不要保存关卡。`UE_ALLOW_BLUEPRINT` 保持 false。

前一段没按验收表通过，不开始下一段。

### 7.1 编译工程和启动编辑器变成独立步骤

改 `plan_sequence` / `_try_cpp` 的分流，不动图的边。

- 句里是「编译工程 / 编译项目 / 编译一下工程」，并且没有「新增 / 加函数 / 改一下 / 实现」时：步骤是 `cpp_build`，不要求唯一类，不注入 `inject_typo`，不改写 `query` 去要求 `apply_unified_diff`。
- 句里明确有「启动编辑器 / 打开编辑器 / 启动 UE」时：`launch_editor` 为真，且不要求 `source_written`。编译前关闭编辑器的现有行为保留。
- 句里同时有「改函数」和「编译工程」时，仍走现在的改源码步骤，不要被这条例外吃掉。

验收：用原话跑到第 1 步时，记录里这一步的标题是编译工程，而不是「C++ 类不是唯一的」。编辑器若被这次编译关掉，通过后记录里能看到启动结果。源码文件字节不变。失败时留下编译错误原文，不要进入改文件的 `fix`。

### 7.2 一句话里的类按槽位绑定，蓝图先查索引

- 「被 A 拾取」「A 拾取 B」里，A 是拾取者，B 是物体。对不上这种句式就暂停，并写出对不上的原因，不猜角色。
- 每个槽位自己解析。一个槽位零条或多条才算不唯一。两个槽位各有一个类是合法的。
- 蓝图解析顺序：句中 `/Game/` 或 `BP_`；然后 `ue_asset` 里父类对得上、资产名对得上的唯一蓝图；再没有才 `needs: blueprint`，提示一次 `r`。
- `/Game/BP_TestPawn.BP_TestPawn` 这种已有条目必须能被用上，不能再要人填目录。
- `ATestActor` 目前没有蓝图条目。这一格暂停是对的。不要默认创建 `BP_TestActor`，也不要默认生成 C++ 实例。

验收：原话在编译步骤之后，Pawn 槽位写成 `/Game/BP_TestPawn.BP_TestPawn`，Actor 槽位暂停并只问一次路径。用一条写了两个不存在类名的句子，仍应暂停且不创建资产。

### 7.3 测拾取时补上放置，检查改为只读

- 两个槽位都有蓝图或关卡里已有实例时，缺的实例用现有 `add_to_scene_from_asset` 放入。位置要让两者距离小于 100 uu。不保存。
- 删掉「先 `set_properties` 写标签再 `find_actors`」这条通过路径。
- 只读：物体属性用现有 Object 读工具；位置用现有 `get_actor_transform`。工具名以 `scan_mcp_tools.py` 当次卡片为准，对不上就停。
- 裁决文案只引用读到的值：`bAllowPickup`、`bCanBePicked`、是否含 `InteractableActor`、与 Pawn 的距离。四条都满足才是「能」。
- 场景里找不到实例、编辑器 MCP 连不上、读属性失败：这一步失败，不要写成「不能拾取」。

验收：准备一个已经在关卡里、距离小于 100 uu、但没有 `InteractableActor` 标签的 Actor，跑只读检查，结果是「不能」，且该 Actor 的标签和 `bPickable` 与跑之前相同。另一条距离大于 100 uu、标签齐全的，结果仍是「不能」，原因是距离。两条都不保存关卡。

### 7.4 给这句加一条旁路评测

不要放进 `eval/run_eval.py` 的默认三条。

新文件放在 `eval/tasks/side/`，内容就是这句原话的期望步骤，而不是一份巨大的自由 JSON。至少断言：

- 编译步骤不要求唯一类，也不改源码。
- 拾取步骤不会出现 `set_properties`。
- Actor 蓝图缺失时序列暂停，退出码非 0，并且不会去创建蓝图。

`check_routes.py` 继续管图的边。这条管的是 `plan_sequence` 的拆句。能不连真编辑器断言的部分放在离线检查里；必须连编辑器的部分沿用 7.3，不写进默认连跑。

### 7.5 以后再做：动作目录

7.1 到 7.4 仍然是在加正则。组合句再多几类（「把 A 附到 B 上」「看日志里有没有这行」）还会再长。目录做在这四段之后。

每个动作一条记录：`id`、参数槽、是否写场景、用哪个现有执行函数、怎样算做完。模型只许从这些 `id` 里挑，并填槽位名。代码负责把槽位解析成路径，解析失败就暂停。禁止模型发明工具全名和 `/Game` 路径。

这就是 5.1 的编排器：模型选已知动作，代码固定执行和裁判。不要在 7.1 之前做。

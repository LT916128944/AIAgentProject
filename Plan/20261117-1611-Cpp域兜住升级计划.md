## 0. 三句话结论

1. C++ 是本仓**最成熟的域**：`CATALOG` 有一等动作 `edit_cpp / apply_spec / compile_project`，验收是硬判据 `cpp_build`，且已有**编译错误回灌**（`build_error.py` + `check_build_error_loop`）。
2. 缺的不是“兜不兜”，而是**“模型产出的代码没被 Spec 化”**——`edit_cpp` 是自由代码生成，改哪儿/加哪个成员/动哪个模块靠模型自由发挥；失败回灌只到“编译级”，逻辑错不可验。
3. 本域升级 = 把“自由 codegen + 编译回灌”**收口成 C++ Spec 边界**（类/成员/函数骨架/编译单元/模块依赖），并把回灌做成结构化闭环；覆盖面补 `.Build.cs` 依赖、新模块、反射宏等。

## 1. 现状与证据（实测）

| 项 | 现状 |
| --- | --- |
| 一等动作 | `edit_cpp`（编辑源码）、`apply_spec`（按 spec 生成/改）、`compile_project`（编译） |
| 验收 | `cpp_build`（编译 exit 0），`_KIND_BY_ACTION` 有映射；`_delivery_criteria` 认 |
| 回灌 | `agent/build_error.py`：编译错误解析→回灌模型改→重编（`check_build_error_loop` 钉） |
| 守卫 | `check_cpp_edit_scene`（“加一个/添加”误判成改码的坑）、`check_solver_patch`（一处替换复用编译管线）、`check_build_error_loop` |
| 路由 | 命中 `edit_cpp/apply_spec` 即走；否则规划者/求解 |

**结论**：C++ 兜得住“编译对”，兜不住“结构可控 + 逻辑对不对”。缺口在 **Spec 化与更细的验收**，不是从零建。

## 2. 本域“模型-脚本”边界

- **模型**：产 **C++ Spec**（要建哪些类/加哪些 UPROPERTY/UFUNCTION、函数骨架与签名、落在哪个编译单元/模块、需要哪些 include/依赖、verify 断言）。
- **脚本**：把 Spec 落成源码 diff（`apply_unified_diff`/`apply_spec`）→ 编译（`compile_project`）→ 解析编译错误 → **结构化回灌模型**（哪个文件/行/符号/错误码）→ 重编（≤2 次）。
- **硬规矩**：模型不直接 `apply_unified_diff` 盲写；只产 Spec/diff，落地经写闸（`allow_writes`/`save`）与编译复核。写场景/源码仍受 `UE_ALLOW_*` 与 `save` 策略约束。

## 3. C++ Spec 草案

```jsonc
{
  "target_module": "AIAgentProject",
  "build_deps": ["EnhancedInput"],           // → 写 .Build.cs 的 PublicDependencyModuleNames
  "files": [
    {"path": "Public/FpsHealthComponent.h",
     "add": [
       {"kind": "UCLASS", "name": "UFpsHealthComponent", "parent": "UActorComponent"},
       {"kind": "UPROPERTY", "macro": "EditAnywhere, BlueprintReadWrite", "type": "float", "name": "MaxHealth", "default": "100.f"},
       {"kind": "UFUNCTION", "macro": "BlueprintCallable", "ret": "float", "name": "GetHealthPercent", "body_hint": "Health/MaxHealth"}
     ]}
  ],
  "verify": ["编译通过", "存在 UPROPERTY MaxHealth", "存在 UFUNCTION GetHealthPercent"]
}
```

## 4. 分期

- **P0 清点（0.5d）**：用 `scan_mcp_tools`/已有一等动作，列清 `edit_cpp/apply_spec` 现能覆盖的形态（新类/加成员/改函数体/新模块/依赖）。
- **P1 Spec 化（2d）**：`agent/cpp_spec.py`：`validate_cpp_spec` + `build_cpp_spec`（Spec→diff→编译）+ 只读复核（编译过 + 反射宏/成员存在可用 `query` 工具或读回源码断言）。
- **P2 回灌收口（1d）**：把 `build_error.py` 的编译错误**结构化成**“文件/行/符号/错误码/建议”，接 §总览的修复闭环（≤2 次），并把“逻辑不可验”的缺口在终态点名（不假装全过）。
- **P3 覆盖面（1–2d）**：`.Build.cs` 依赖、新 Module、`GENERATED_BODY`/`UINTERFACE`/`UENUM`、Blueprint 可调用接线；每类配断言。
- **P4 沉淀（0.5d）**：稳定形态（如“加一个带 MaxHealth 的血量组件”）经 distill 毕业成 learned 快路。

## 5. 守卫

`check_cpp_spec.py`（kernel 确定性/幂等/编译回灌闭环/终态可解释）、`check_cpp_route.py`（“改射速×100/加组件/加模块”稳定进链）、复用并扩展 `check_build_error_loop / check_solver_patch`。登记 `offline.yml`。

## 6. 风险与取舍

- C++ 是高风险写面：**Spec 化不等于限制表达力**，自由代码生成仍保留，但“改源码前必须有 Spec/目标 + 编译复核”。
- “逻辑对不对”无法只靠编译验：终态要**诚实**区分“编译过”与“行为未验证”，不许把编译过当功能完成（沿用 `_delivery_criteria` 的假成功防线）。

3. 把编译错误回灌结构化成“可喂回模型”的形状，接修复闭环。
